## Confirmed mechanisms and attribution boundary

The owner's installed browser, settings and service-worker error log are unavailable. **The exact original installed incident trigger is not established.** The following defects were established in source and reproduced with the actual background script and real imported extension modules, using simulated Chrome APIs:

1. `buildMenus().finish()` clears native entries with `removeAll()`. If any subsequent `create()` callback fails or times out, its catch clears everything again and throws. There was no functional recovery root. The new explicit test first registers successfully, fails a destination in a later rebuild, and proves the old code ends with an empty native menu. This is a confirmed mechanism for the reported missing menu, not proof of which Chrome error occurred on the owner's machine.
2. Toolbar `onClicked` invokes `sidePanel.open()` directly, correctly preserving the gesture, but rejection only writes a console warning. No UI opens. A synchronous throw or unavailable API also escapes that recovery path. Injected panel rejection reproduces the user's no-interface symptom. The original rejection reason remains unknown.
3. `applyToolbarOpenMode()` awaits Shelf configuration before applying the saved popup choice. A configuration rejection prevents `action.setPopup()` from running. The manifest had no default side-panel path, leaving cold initialization dependent on the asynchronous setup call. These are confirmed coupling/initialization weaknesses; they are not an invented explanation for the owner's exact Chrome state.
4. Menu rebuilding was registered for browser startup and installation, not every service-worker activation. `runtime.onStartup` does not mean worker restart. If a prior rebuild left menus empty, restarting a Simple/Narrow worker alone did not restore them. The existing Level alarm alone could not cover that case.

Full background evaluation with real `importScripts` dependencies reaches toolbar, menu and message listener registration. No syntax/import/startup exception was reproduced in this environment. Therefore a single service-worker startup crash explaining both symptoms remains unconfirmed. No import errors were suppressed or critical modules skipped.

## Production fixes

- Keep the existing V3/Legacy projection and serialized `menuRebuildQueue`. Within that lane, acknowledge a REDOWN root and the existing **Manage destinations…** action before cache/profile/inventory processing. Update existing entries first to preserve children; create missing entries only when needed. Use native callbacks, bounded acknowledgement and callback-scoped `runtime.lastError`.
- Keep validated parent-first full registration. Remove the destructive failure cleanup that erased an already acknowledged root. Any removal, projection, cache, snapshot or native-create failure attempts the same minimal local access recovery before recording failure. A subsequent Apply/startup uses the same existing lane. Partial registration never reports Saved.
- Reconcile on worker load as well as browser startup/install; catch event-triggered rejections explicitly. No new alarm, scanning engine or diagnostic subsystem. Competing events serialize. The recovery action opens the existing local Explorer and requires no Cloudflare inventory.
- Invoke Shelf open synchronously inside the toolbar gesture, with no preceding storage/discovery/menu wait. Catch promise rejections, synchronous errors and unavailable APIs. Open the existing local `shelf.html` in an active tab when panel opening fails; if tab creation fails, attempt Chrome's supported `openOptionsPage()` escape. If Chrome rejects all opening APIs, log the failure honestly.
- Add manifest `side_panel.default_path: shelf.html`. Retain the existing asynchronous per-preference setup, but a failed Shelf configuration no longer prevents applying the saved popup preference. Normal popup choice remains native `popup.html`; no preference is rewritten by recovery.

The normal replacement still has a short remove/create interval; Chrome provides no transaction across context-menu entries. This is not a claim of atomic registration. An interruption during that interval is reconciled on the next worker activation. A Chrome-wide registration denial cannot be repaired by extension code; it remains failed, and independent toolbar/local access remains available where Chrome allows it. Recovery does not automatically replay a transfer or invent an authorized destination.

Simple, natural Narrow, selected-bucket Level, ordering, labels, click resolution, transfers, Explorer, Shelf documents, Split View and account/configuration stores are preserved. The only production files changed are `extension/background.js` and `extension/manifest.json`. No future Settings repair controls, diagnostic dashboard, new error framework, support reporting, permissions or provider changes. `NEED_TO_DO/10312026.md` is untouched.
