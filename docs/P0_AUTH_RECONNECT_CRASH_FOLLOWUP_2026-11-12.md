## Implemented behavior

**Navigation and recovery:** Known accounts retain GO TO, including expired/revoked extension authorization, unavailable APIs and stale checks. It opens the existing provider URL and never runs OAuth or retries a save. An independent 32 px button beside it has the tooltip/name “Reconnect [provider]”; it remains available in GO TO state. Initial storage reads show a checking state. Explicitly unconnected/disconnected accounts show LOGIN; ambiguous legacy or failed status reads retain useful navigation with an unknown/unverified message. No website cookies, hidden tabs or invasive login probes were added.

The icon reuses `googleDriveOpen`, `dropboxConnect` or `onedriveConnect`. Exact Shelf, Options and Popup senders can invoke their recovery/status commands; cancel/disconnect and diagnostic authority remain separately restricted. Options has explicit recovery controls outside Debug Mode; Popup has a compact “Reconnect clouds” disclosure. A broken Shelf therefore has a supported alternative when the background core still works. A wholly unavailable extension cannot be repaired by a button that cannot execute.

The shared projection distinguishes account knowledge, cached observation freshness, required scopes, OAuth, provider reachability, destination checks and available verified transfer evidence. It never claims website session visibility or guaranteed future upload readiness. Null last-save evidence is unknown in this compact projection, not proof no earlier verified receipt exists; History and the durable receipt ledger retain ownership. A source-phase ONEDRIVE_NETWORK does not itself establish a Microsoft outage. Original cloud icons, ordering, navigation URLs, counts and verified SUCCESS semantics remain.

**Google:** Revoked/not-granted errors become `GOOGLE_AUTH_REQUIRED`, blocked/auth phase, with preserved account data. The native path no longer emits AUTH_CHECKED or admits a new job solely from connected state. Existing noninteractive identity verification must succeed for the same account first. The explicit icon can invoke Google's real existing consent flow. An account change fails closed, preserving old jobs/destinations; this is a recovery flow, not an implicit account-switch command. The two exhausted uncertain jobs are never reset or automatically replayed.

**OneDrive:** Network, 429 and 5xx failures preserve stored refresh credentials and exact identity/root bindings and expose temporary unavailability, not invalid grant. Retry cooldown is 15–300 seconds (normally 30 s, honoring bounded Retry-After). Concurrent checks join; recent account checks are briefly cached. Invalid grant/scopes/401/403 permit explicit official reauthorization rather than an endless passive OAuth loop. Successful same-account reauth preserves connection ID; different account/drive/root is rejected before replacing credentials. Passive status display never opens OAuth. Missing extension credentials require reconnect while meaningful website navigation and prior destination fields survive.

**Dropbox:** Healthy refresh uses the existing session silently; temporary network/5xx checks do not force OAuth. Same-account/namespace reconnect preserves connection ID. Existing explicit `dropboxStatus` remains awaitable and completes ID-based receipt reconciliation before replying; it never repeats finish/upload. Shelf requests use `passive:true`, coalescing checks and returning a clearly pending/cached projection. Explicit status calls retain their stronger completion behavior. Google/OneDrive use the same passive-versus-explicit distinction. Provider checks remain asynchronous and do not serialize unrelated providers, Shelf rendering or native menu ownership. Ten concurrent Google native attempts share one actual in-flight grant check; failed checks admit no jobs. Provider HTTP requests retain their existing 25-second budgets. Chrome identity/IPC calls can still settle late and cannot be forcibly cancelled by this recorder; passive display remains independent, and no hard process-kill guarantee is claimed.

Provider-specific auth/HTTP/history/restart codes and origin phases survive existing History/Queue/attempt projections. A successful-looking navigation, consent dialog, HTTP acknowledgement or animation is never a verified save. No new counter engine or generic replay action was added.

## Incident migration and health continuity

The disk-backed CAPLESS segment backend `redown-capless-archive-v1` is **byte-for-byte unchanged**. Confirmed ON/OFF/RAW consent, archive ID, immutable closed chunks, sequence/digest chain, gaps and existing exports are preserved.

The separate incident database upgrades non-destructively to version 2:

- Existing `incidents` rows remain untouched, including all 16 legacy pinned envelopes. Upgrade copies them once into append-only `incidentHistory`, retaining stable event IDs, timestamps and payloads.
- New actionable faults append to history in atomic transactions, requesting strict durability where supported. A separate `incidentIndex` holds at most 16 **references** for fast display. Evicting a reference does not delete an envelope. Normal ambiguous worker endings remain lifecycle observations/checkpoints and no longer create pinned faults.
- Genuine incident-storage errors signal `INCIDENT_STORAGE_UNAVAILABLE`; consecutive warnings are suppressed until a successful persistence. Important new faults can persist after a legacy 16/16 store. Repeated identical fault codes are coalesced within one second; CAPLESS lifecycle capture still receives its observations before pin handling.
- `ARCHIVE_STALLED` is an active observed archive condition; `PINNED_CACHE_FULL` identifies the preserved legacy cache; `HISTORIC_CAPTURE_INCOMPLETE` retains earlier uncertainty. Current health, historical health and incident counts are separate. Historical counts/flags are preserved, not erased to make the UI green. A late successful core checkpoint resolves its outstanding uncertainty and records latency.
- Overall captureIncomplete may remain true for historical loss. It no longer means the immutable archive is actively stalled. Current flags are observations with a timestamp and collector scope, not a guarantee that all contexts/future writes are healthy.
- Complete export streams/chunks **all** incident pages, not only the fast index. The fallback produces bounded ZIP parts (64 incident rows/page); streaming uses the existing reviewed file-picker path. It also works when no capless archive was initialized, with an explicit not-started manifest. Snapshot boundaries, hashes and unconfirmed writes remain explicit. The old incident-delete control is now honestly labeled “Clear fast incident index”; it never deletes durable history or original legacy evidence, even when explicitly used. No deletion is required as a repair.

The additive incident DB version upgrade is forward-oriented: old v1 readers cannot open the v2 incident database after rollback. Keep reviewed local exports/forward-compatible readers; never delete the DB to downgrade. The main CAPLESS segment database stays at its original version.

There is no incident-history TTL/rotation or automatic forensic deletion. Browser quota/eviction and OS termination still apply, and different IndexedDB databases can share origin quota. Export bodies are chunked; very large ZIP entry metadata can still grow, so multipart export remains appropriate for very large archives. Always-on history records meaningful faults, not an endless stream of routine epochs. Hard termination can beat any async commit; integrity of committed chunks is not proof every pre-crash event was captured.
