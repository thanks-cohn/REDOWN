# Approved Chrome acceptance: Shelf and attached pop-out

Run in a Chrome environment allowing unpacked extensions. The managed browser used for automated work cannot install REDOWN. Preserve existing user storage; use a disposable profile/source copy for injected failures. These steps are pending manual acceptance, not passing installed results.

1. Load the audited `extension` package in a new Chrome profile, with no local/session storage, Cloudflare login, accounts or buckets. Pin REDOWN. Click the real toolbar icon immediately after installation and again after cold worker startup. Expect the existing Shelf, no mini-dashboard, tab or detached window. Record errors shown by `chrome://extensions` and the worker console.
2. Repeat over an existing profile without clearing settings. Check destinations, History and V3 menus on a normal HTTPS page. Shelf remains the default; an intentionally saved Popup choice must remain Popup. Old values already overwritten by the previous build cannot be inferred; explicitly reselect the desired mode.
3. Choose Popup in Shelf Settings or existing Extension options. Click the actual icon. Expect only Chrome's native compact panel attached to that icon. Dashboard, sign-in and Settings remain user-invoked actions; verify these with no OAuth login.
4. Select Shelf again. In disposable worker DevTools save `const savedShelfOpen = chrome.sidePanel.open`, then temporarily assign `chrome.sidePanel.open = () => Promise.reject(new Error('test rejection'))`. Click the actual icon, not a console call lacking its gesture. On Chrome127+ the launcher attempts native `action.openPopup`. If Chrome accepts, visually confirm the compact panel is anchored to the icon and no new tab/window appears. Record whether it was same-click; do not assume success from a promise alone.
5. Force `action.openPopup` to reject in that disposable worker while Shelf rejects. Click once: expect a badge/tooltip explaining another click. Click again: Chrome must open the armed native popup and suppress the worker's Shelf listener. Restore methods or reload. The local popup script consumes recovery without changing the saved mode; after closing the popup, the next dispatched click should attempt Shelf again.
6. Restore Shelf opening while recovery is visible. Click Retry Shelf. The attached popup must close before Shelf is requested. No separate window may appear. Failed Retry leaves a native tooltip; it does not resurrect the popup beside Shelf. Check multiple windows: the recovery URL's original window is the Retry target, not whichever window was last focused later.
7. Test a slow request in the disposable worker: wrap the original API so the returned promise settles later. After the native indication deadline, verify no second interface appears. A late rejection from an expired or superseded attempt must not open a popup. A new explicit click can retry Shelf. Do not interpret a missing page acknowledgement as proof the Shelf is absent.
8. Temporarily throw near the start of `shelf.js` in the disposable source copy, then reload. If Chrome accepts the panel request but the local UI fails, expect `SHELF_READINESS_UNKNOWN` and no automatic second surface. This is a documented unresolved-rendering boundary. Restore the file. For manual access, explicitly open Chrome's Extension options, choose Compact popup and close any Shelf before clicking REDOWN. That preference change is intentional and reversible.
9. Repeat rejection/throw/missing-API tests with a stopped service worker, Chrome restart, extension reload, offline networking, revoked/slow Cloudflare auth, two Chrome windows, rapid clicks and a tab switch during failure. No provider or menu operation may gate the initial Shelf request. Real separate Chrome profiles must be tested independently.
10. To simulate provider import failure, use a disposable source copy that throws after `entry-bootstrap.js` has been imported, reload, then click the toolbar. The registered launcher should remain independent. A main-script parse failure or missing bootstrap can prevent all extension events; record that platform boundary rather than claiming recovery ran.
11. In recovery use Export support report. Alternatively inspect only `entryPointEvidence` and `rightClickMenuStatus` through extension DevTools. `ATTACHED_POPUP_ACCEPTED` means Chrome accepted the API request, `ATTACHED_POPUP_NEXT_CLICK` means the native route was armed, and `ATTACHED_POPUP_BLOCKED` means registration/targeting failed. Do not export all storage or provider credentials.
12. If Chrome blocks both supported routes, expect a native indication/local failure record and zero unsolicited tabs/windows. Test unpinned icon placement too: Chrome controls where its action bubble is anchored; no custom window can imitate or guarantee toolbar placement.

Record Chrome/OS, profile type, extension build hash, normal/forced failure, actual anchor location, before/after tab/window counts, saved preference, native menu visibility and screenshots. Keep source fixtures, API acknowledgement, rendered visual behavior and provider behavior as separate evidence tiers.
