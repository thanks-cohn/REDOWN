# Explorer diagnostics implementation stages

## Stage A — architecture and portable diagnostic core

Existing surfaces were inspected before implementation. Project API0.1 navigates pinned source, debug0.1 reads historical incident journals, semantic API models proposed relationships, and runtime1.0 records bounded HTTP/message observations. Runtime1.0 cannot return an Explorer operation timeline or exact identity comparisons. None safely executes a remote agent command. Frozen historical contracts/hashes remain unchanged; no accepted Forever model exists. New Explorer diagnostic1.0 is an additive domain-specific adapter, reusing the same dependency-free collector pattern and Debug authorization boundary rather than replacing these namespaces.

Machine map: `agent/explorer/model.json` connects23 Explorer operations, source symbols, DOM identities, state owners, messages, retrieval mechanisms, transformations and tests. `validateArchitecture` exposes unresolved/stale anchors; these are implementation-navigation observations, never runtime/Forever intent proof. The offline `agent/explorer/cli.mjs` adds no credentials/network/execution surface.

Core:64 operations×64 events maximum,24h retention,262144-byte export cap; HMAC-SHA256 identities scoped to a random run key that is never exported. Unknown raw fields, tokens, URLs and names are dropped. Whole import validates before application. Restart can mark unfinished work unknown; eviction/truncation and observation-only outcomes remain explicit. Diagnostic rules distinguish HTTP404 from a source lookup miss, compare exact key/bucket fingerprints only in the same scope, and compare API successes with Worker failures without inventing a root cause.

StageA tests: six new core/API cases passed (HMAC/privacy,404/path divergence,identity drift,atomic malformed import/bounds,retention/restart/disabled collection,portable queries). Runtime instrumentation and installed/deployed evidence are not part of StageA; they follow separately. No incident is closed by this stage.

## Stage B — extension/Worker boundaries and Debug inspection

Added optional bridge adapters, explicit per-message IDs/parent links, same-scope HMAC context shared only through the sender-checked Debug channel, safe Worker protocol1 evidence, and Debug-only inspection/review/export/clear controls. Literal message keys, OAuth path encoding and Worker query encoding are distinguished. Cross-Worker response evidence includes version/capabilities, declared-binding comparison, source read, destination write/read-back and cleanup stages; missing/older protocol evidence remains unknown. Root UI wrappers preserve return values and do not guess asynchronous parentage after an await. UI-only completion stays unknown unless a specific boundary supplies its result. HTTP404 is retained as an observation instead of universally relabeled “missing object”.

Extension version is0.5.14. New deployments/explicit repair ship Worker6 with diagnosticProtocol1; safe-transfer compatibility still accepts existing Worker5, whose unavailable diagnostic details are not invented. Collection does not provision or repair Workers. Manifest adds no permission. The allowlist includes the three new diagnostic scripts. Original project/debug/runtime API versions are unchanged; one additive Debug handler updates the current message inventory/count only.

All collection is Debug-gated, independently of Beta. UI state snapshots on inspection expose counts, booleans and HMAC identities, not raw filenames/accounts. Background redacted observations persist locally, bounded to24h/64 operations/64 events/262144 bytes; incomplete restored work becomes unknown. Diagnostic clear/disable handles pending save races and removes retained records. An operation query can include retained descendants; explicit truncation and missing parents remain visible. Worker event order is meaningful; collector timestamps record receipt, not measured Worker stage duration.

Cross-boundary tests run real background/embedded Worker with in-memory R2, including a deliberately wrong-binding404 fixture and successful verified copy; no live cause or resolution is claimed. StageB full suite:237 tests,230 pass,seven unchanged baseline failures. Targeted core/bridge/Worker/UI checks pass. Existing auth harness now loads the real new dependencies; existing assertions remain. Normal download terminal-state and mode tests remain intact.

User follow-up: preview URLs previously refreshed only when reopening the file. `refreshVisible` now refreshes connected disclosures for the exact changed account/bucket after Attach and profile storage changes. A WeakMap avoids retaining detached preview nodes. Tests prove expansion is preserved, other buckets and detached previews are unchanged, and the media blob is not replaced. The UI still labels configured URLs as unverified for public file accessibility.

Ordinary Chromium154 rendered the actual Debug inspector at1366 and390 widths with simulated bundles/messaging/clipboard/download, including trace selection and review-before-download. This is browser UI fixture evidence, not installed-extension, OAuth or live R2 evidence. Detailed coverage, schema/fault/CLI checks and current404 case follow in StageC.
