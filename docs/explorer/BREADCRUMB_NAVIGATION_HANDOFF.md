# Modular breadcrumb implementation handoff

## Page 1: Implementation and architecture

30 October 2026. Branch: `release/cloudflare-true-remote`. This is an implemented navigation foundation with local functional verification. Browser visual acceptance, compositor performance and installed-extension acceptance remain pending. It is not a release certificate.

The modern Explorer now places breadcrumbs in their own bounded section immediately below the existing toolbar. The root, intermediate hierarchy and current directory have distinct typography and spacing. The second directory starts with its first word; deeper collapsed directories show a Unicode grapheme initial. Only persistent expansion introduces intermediate rows. Rows are always ordered by path depth, regardless of click order. Each row has a stationary left anchor and a separately scrollable descendant trail. Long anchors truncate accessibly; the full name remains in the accessible label and title. The intermediate region scrolls vertically beyond 260 px or 32dvh.

Hover and keyboard focus reveal full names inline with a 160 ms maximum-width transition and 120 ms opacity transition. The left edge of the hovered control stays fixed while descendants yield space. No hover JavaScript, directory mutation or file-list rendering is involved. Persistent expansion uses short transform/opacity row transitions. Separate minus controls collapse rows. Direct-navigation mode retains separate plus controls for explicit expansion. Directional overflow controls, contained native horizontal scrolling and scoped arrow/Home/End focus navigation expose hidden descendants. Native Enter/Space activation remains available.

**Public interface.** `extension/beta/breadcrumb-navigation.js` exposes `RedownNavigation.model(location)`, `rows(hierarchy, expandedSet)`, `register(id, factory)` and `createSlot(host, contract, id)`. The model supplies immutable `{id, fullName, prefix, depth, current}` entries. IDs include account, bucket and exact prefix; repeated names, literal encoding, empty components and Unicode stay distinct. It never decodes keys. The contract contains `current`, `hierarchy`, `settings`, `themeTokens`, `onNavigate(entry)` and `onPreferencesChange(settings)`. The host provides actual available geometry; the renderer measures its own row viewports and observes host resizing. Explorer retains sole ownership of the current directory, history and navigation guards. Its existing `navigate()` handles all requests.

**Replacement.** Register a factory returning `{update(contract), destroy()}`, then select it through `slot.select(id)`, or pass its ID at slot creation. A minimal replacement is covered by a test. Registration rejects duplicate IDs. Changing renderers requires no file-operation or provider edits. The built-in ID is `expandable-hierarchy`. Destroy removes component listeners, observers, pending frame work, animations, styles' root class and owned DOM.

**Isolation and performance.** All new selectors begin with `.rd-bc`; there are no global resets, theme overrides, keyframes or new `!important` rules. Colors use inherited Explorer tokens. Layout/style containment, a local stacking context, clipped surfaces and contained scrollports bound the presentation. Explorer shortcuts ignore active breadcrumb controls. Delegated component listeners handle clicks and keyboard input; one ResizeObserver and a coalesced animation-frame callback measure overflow. The model is cached by exact location, and unchanged hierarchy/settings references skip rendering. Row DOM and independent scrollports survive expansion changes. Hover layout transitions are intentionally bounded, not asserted to be compositor-only. Explicit expansion uses batched geometry reads and transform transitions; removed rows disappear immediately while retained rows reposition. Preferences retain at most 512 expansion identities.

**Settings.** `chrome.storage.local.betaExplorerNavigation_expandableHierarchy` contains `expandBeforeNavigating` (default true) and `expandedIds`. Preferences survive ancestor navigation and are account/bucket scoped by identity. A late initial storage read cannot overwrite a user interaction. Storage errors report locally. Other presentation modes can use separate keys.

**Completed local checks.** Ten dedicated tests pass: compression and exact prefix identity; arbitrary expansion ordering and independent collapse; direct navigation with separate expansion; hover isolation and retained DOM; independent scrolling and renderer replacement; 500-level ordering/ownership; selector scoping; reduced-motion and lifecycle cleanup; malformed saved data; runtime asset loading/packaging inclusion. Eleven adjacent login/appearance tests pass, for **22 focused checks passing** across the two focused commands. Syntax and whitespace checks pass.

**Collision and accessibility evidence.** Automated checks establish selector scoping, unchanged outside controls in the fixture, local keyboard handling and separation of expand/collapse from navigation. Controls have full-name accessible labels, expansion state where appropriate, current-location semantics and visible focus styles. These do not constitute screen-reader, zoom, native scrolling, stacking or theme visual acceptance. Event/observer cleanup and reduced-motion animation suppression are exercised with mocks. Heap profiling and long-running memory stability are unmeasured.

**Performance evidence.** `dom-timing.json` records 100-level construction and 1,000 unchanged updates under Node/jsdom. Those numbers exclude CSS layout, paint, GPU and real input latency. They cannot establish 60 FPS or a 16.7 ms browser-frame budget. No idle animation loop or pointermove handler is present. Real-browser trace collection and hover/scroll smoothness remain unverified.
