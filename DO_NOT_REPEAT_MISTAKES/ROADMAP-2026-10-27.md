# REDOWN Roadmap — 10.27.2026
**Repository:** `thanks-cohn/REDOWN`  
**Working branch:** `beta-explorer`  
**Location:** `DO_NOT_REPEAT_MISTAKES/`  
**Priority:** CRITICAL — working product before further engineering projects  
**Production rule:** Original/Legacy Cloudflare Explorer remains the default and unchanged; Beta is opt-in. No automatic promotion.

## Owner's intent
Make the new Beta Explorer a REAL Cloudflare R2 file manager first: login, discover authorized accounts/buckets, show actual objects, and let the user perform ordinary mouse, keyboard, context-menu and transfer operations. Then implement a useful docked right-side Preview pane. Only AFTER a live working GUI is established, undertake a comprehensive, continuing audit of Legacy versus Beta examining not merely WHAT a feature does, but WHY, HOW, WHEN, failure behavior, and evidence. Use that audit to design guided real-GUI test sessions exporting inspectable JSON.

Do not substitute simulated demonstrations, architecture diagrams, a testing laboratory or a checklist for working installed-extension functionality.

## Milestone 1 — Login → real files → real operations (IMMEDIATE)
1. When Beta opens, reuse existing Cloudflare session, load accessible accounts and buckets automatically, restore the previously selected valid bucket/folder, and list actual R2 objects. For a sole bucket open it directly; for multiple buckets and no prior choice provide an immediate obvious choice. Avoid unnecessary separate manual setup clicks.
2. A bucket is a navigation destination, not an engineering configuration wizard. Keep operationally necessary provisioning/binding/recovery logic intact; do not delete functioning code to hide unsightly buttons. Move advanced controls to a secondary interface only once the new path has been tested.
3. Provide ONE prominent Refresh action in the Explorer header: refresh live files and discovery; inspect connection/readiness when necessary; offer safe, explicitly authorized repair where possible. Show loading, empty, permission-denied, expired-auth, partial-failure and recoverable states distinctly. Do not silently mutate provider permissions or resources.
4. Actual file list and folder hierarchy: path, history, selection, sort/filter, grid/list, readable metadata, loading/progress and errors. The UI must distinguish real R2 results from fixtures.
5. Functional interactions: left-click selection, double-click open/preview, right-click context menu, keyboard shortcuts (Copy/Cut/Paste, F2, Delete, navigation), drag/drop upload or move as supported, toolbar actions. Right-click commands should be context appropriate: Open/Preview, Download, Copy, Cut, Paste, Duplicate, Move to/Copy to, Rename, Delete, Properties, Refresh, and other supported original actions. Do not expose non-working items.
6. Route Beta operations through the ONE universal file API and existing production Cloudflare/Worker services where appropriate: list/stat, upload/download, mkdir, copy/move/rename/delete, TRUE REMOTE. Check that each GUI action reaches its backend, reports outcome honestly, updates the visible list, and handles uncertain outcomes without replaying writes blindly.
7. Preserve original Chrome right-click TRUE REMOTE and original Cloudflare Explorer completely. Use explicit disposable R2 test namespace and owner authorization for writes/deletions.
8. Acceptance is not code presence: installed Chrome must show actual bucket contents and successfully complete a real upload → independent readback/SHA-256 → copy → rename → nested move → download → deletion workflow. Verify original and Beta TRUE REMOTE entry points with authorized safe URLs. Include actual 51 MiB transfer and document real method limits; never claim unrestricted sizes.

**Exit gate:** owner can log in, view real files, operate on them using normal GUI controls, refresh, and observe correct results in R2; evidence is recorded. If live credentials/authorization unavailable, document blocker as UNVERIFIED instead of PASS.

## Milestone 2 — Right-side docked Preview pane
- Add a genuine Preview button to reopen the pane after minimization or closure.
- Pane docks on the RIGHT of the file list, updates when file selection changes, and supports image, PDF, text/code, video and audio as feasible using bounded reads and existing API.
- `−` MINIMIZES to a compact pane header/tab without discarding selected-file state; `X` CLOSES completely, allowing the file list to reclaim space; Preview reopens from either state.
- Support resize by dragging the divider, plus an EXPAND affordance. Expanded preview should be allowed the whole available Explorer height, with sensible width controls. Distinguish height maximization from closing/minimization. On narrow viewports offer a suitable overlay or stacked presentation rather than crushing file rows.
- Manage object-URL and media-player cleanup, abort obsolete reads, keyboard/focus accessibility, loading/error/unsupported format states and metadata. A preview failure must not block file operations.
- Test on real R2 files, including unsupported/corrupt/large media. Confirm close/minimize/reopen/expand and navigation work without losing the file list or selection.

**Exit gate:** functional side preview with proper minimize/close/reopen/expand controls tested in installed Chrome, not a static mock.

## Milestone 3 — Comprehensive, living Legacy ↔ Beta investigation (AFTER real GUI)
Do not conduct only a high-level checkbox exercise. Audit every discoverable original user-facing control, action, shortcut, dialog, state, transfer path, Worker path, configuration rule, format, limit, error mode and supported workflow, including subtle and indirect behavior. Treat this as a continuously extensible inventory rather than a finite marketing checklist.

For EACH capability record:
- **WHAT:** observable behavior, arguments, inputs/outputs and user benefit.
- **WHY:** original design purpose, safety rationale, provider constraint or historical reason; distinguish code-supported facts from inferred or unknown intent.
- **HOW:** event handler → API/background → Worker/provider operation; dependency, timing, persistence and failure path.
- **WHEN/CONTEXT:** trigger, prerequisites, account/bucket/folder context, permissions, size/format cases.
- **WHAT IF:** errors, retries, ambiguous writes, cancellation, concurrency, corruption, auth expiration, network loss and recovery; user messaging.
- **LEGACY:** implemented/actually verified distinction and supporting references.
- **BETA:** exact counterpart, changed semantics, improvement/regression, actual verified state and supporting references.
- **GAP/DECISION:** missing, equivalent, intentionally redesigned, unsafe to copy, obsolete, or awaiting verification, with rationale and priority.
- **TEST/EVIDENCE:** reproducible real-GUI steps, expected/observed states and linked machine-readable outcomes.

Make the comparison traceable to source paths/line ranges and test evidence. Do not assert original feature parity without inspecting and exercising it. Capture Beta-only improvements separately; do not demand reproduction of bad Legacy UX. Keep functional equivalence, operational safety and user goals more important than identical appearance.

Initial discovery areas: auth/account switching; bucket readiness/destination profiles; Simple/Nested context-menu editing; browsing/search/sort/list-grid; multi-select/clipboard/right-click/drag-drop; upload/download/large files; TRUE REMOTE URLs and provenance; transfer conflicts/verification; archives ZIP/CBZ and per-entry actions; all previews/3D/zoom-pan; public URL handling; notifications/history/recovery; shortcuts/accessibility; filesystem/path encodings; provider restrictions and user preferences. Include originally unsupported operations honestly.

**Exit gate:** a durable source-backed feature ledger showing WHAT/WHY/HOW/WHEN/FAILURES and current real verification for Legacy and Beta, with no unsupported 'full parity' claim.

## Milestone 4 — Guided GUI test sessions → reviewable JSON
Once the real Explorer works and the comparison ledger has useful coverage, create a lightweight opt-in Guided Test panel *inside the same Beta GUI*. The user performs ordinary controls; do not build a disconnected laboratory.

- Organize long, varied sessions into thematic sections and unique exercises; avoid repeating identical exercises within a session; revisit across sessions with varied inputs, formats, sizes and error cases.
- Tests must exercise real application code and approved disposable cloud objects. Never operate on production user data without explicit scope.
- Record instruction, prerequisite, exact UI action, universal API operation, correlation ID, timestamps, provider response, bytes/duration (where available), measured memory/latency when supported, independent verification (hash/readback or appropriate checks), actual versus expected, and outcome: PASSED/FAILED/BLOCKED/NOT_TESTED/UNCERTAIN.
- Track baseline, progress, attempted cases, safely resumable session state and coverage by feature/variant. Do not mistake user clicking 'Next' for successful verification.
- Export versioned JSON that can be brought back to ChatGPT for failure analysis. Redact auth tokens, signed URLs, secrets and sensitive filenames where possible. Never claim telemetry that was not collected; indicate missing fields.
- Keep instrumentation lightweight by default, with more expensive detailed diagnostics opt-in.
- Use the living feature ledger to derive coverage and expand future sessions, including interruptions, unauthorized requests, duplicate names, unusual Unicode, large files, corrupted files, conflicts, and uncertain provider outcomes.

**Exit gate:** owner completes actual GUI exercises and exports evidence JSON that distinguishes verified successes from unverified and failed actions.

## Addendum — Bring Your Own S3-Compatible Provider (future Beta expansion)

**Intent:** After Cloudflare R2 Beta is working and independently verified, extend the SAME universal file API with a genuine S3-compatible storage adapter. Let users bring their own S3-compatible providers and accounts rather than requiring Cloudflare. Preserve Cloudflare-only Legacy as the stable initial-launch experience; multi-cloud remains opt-in Beta functionality until accepted.

### Proposed user experience
- **Add Storage Provider → S3-Compatible**: select a known provider preset or choose Custom S3.
- Collect only necessary connection parameters: endpoint URL, region when required, supported addressing style, bucket scope and narrowly permissioned credentials (or an appropriate provider-specific authentication method). Clearly identify required fields, connection type and applicable provider caveats.
- **Test Connection** without writing or provisioning resources: validate endpoint, authorization, bucket listing where permitted, and actual read access. Some providers deliberately deny bucket enumeration; support manually naming an authorized bucket.
- When connected, display accessible buckets and their files in the SAME Beta Explorer list, toolbar, context menu, navigation and eventually Preview pane, without introducing a separate product or file-management API.
- One Refresh control reloads listings and surfaces actionable connectivity/authentication errors. Connection configuration and secret rotation live in Settings, not the normal file-browsing workspace.
- Show provider identity and precise capabilities/limitations, rather than implying every S3 endpoint behaves identically.

### Architecture and safety requirements
1. Define an S3 adapter beneath the existing universal file API; preserve operation semantics and result/error codes. Do not create a parallel engine. Implement only operations actually supported and tested by the adapter.
2. Support signing/authentication correctly (typically Signature Version 4), endpoint/region validation, virtual-hosted versus path-style addressing as applicable, URL encoding, pagination and continuation tokens, object keys, folders-as-prefixes, and provider-specific metadata/ETag behavior. Do not assume ETag always represents an MD5 checksum.
3. Enforce strict destination scoping; protect credentials and signed URLs from UI logs, error reports and exported test JSON; never embed permanent secrets in shareable client assets. Document browser-extension credential/security tradeoffs and evaluate a secure authentication or broker model before release.
4. Account for CORS and browser restrictions. Provide actionable setup instructions when providers require CORS configuration; never bypass protections or claim universal compatibility.
5. Preserve bounded-memory transfers, multipart support where needed, checksums/read-back verification, conflict rules, idempotence/uncertain-write behavior and safe cancellation. Do not invent arbitrary file-size limits or guarantee operations beyond provider capabilities.
6. TRUE REMOTE is a separate capability: **do not claim generic S3 API access automatically makes provider-side URL ingestion possible.** Investigate provider-native import/copy features or an explicitly opt-in secure remote transfer Worker/relay, verify where bytes flow and who pays bandwidth, and label unsupported providers accurately.
7. Define a tested initial S3 interoperability matrix across at least two independently operated S3-compatible backends after Cloudflare R2; distinguish API compatibility from guaranteed provider coverage. Record connection, list, stat, upload, download, copy, move, rename, delete, multipart, permission, error and cancellation behavior.
8. Future cross-cloud copy/move must verify destination before deletion of a source and must never claim atomicity across independent providers. Defer until each source/destination adapter is trusted.

### Sequencing and acceptance
This addendum is **not permission to distract from current Milestones 1–4**. Finish visible live Cloudflare files, functional operations, Preview, WHAT/WHY/HOW parity analysis and evidence-based guided testing first, or deliberately schedule S3 work only after the owner approves a change in priorities.

**S3 exit gate:** connect an owner-authorized test S3-compatible account, browse actual objects in Beta, complete independently verified disposable-object file operations (including larger multipart cases), document compatibility/security restrictions and produce real test evidence. Only then advertise that provider as supported. Legacy remains Cloudflare-only and untouched.

## IMPORTANT ADDENDUM — MUST PLAN: One Cloudflare Login, Automatic Multi-Cloud Authorization and Customer-Owned Secrets (2026-10-27)

**Status:** FUTURE PRODUCT REQUIREMENT / PROPOSAL, NOT IMPLEMENTED OR VERIFIED.  
**Priority:** After the 60 real GUI exercises, Universal API reliability/CLI testing, and approved Cloudflare transfer release gates. Do not divert current Beta implementation or modify Legacy/main.  
**Related:** Bring Your Own S3-Compatible Provider addendum above; `docs/proposals/REDOWN_COMPETITIVE_LEADERSHIP_ROADMAP.md`.

### Owner's precise desired experience

1. Install REDOWN and sign into the user's **own Cloudflare account** using Cloudflare OAuth. This is REDOWN's central interactive session, not an assertion that Cloudflare identity grants authority over Google/AWS/etc.
2. Choose **Add Cloud** and connect another provider ONCE through its supported authorization flow: OAuth where genuinely supported, short-lived delegated credentials, or a one-time provider API/application-key setup when necessary.
3. With the user's explicit, appropriately scoped permission, REDOWN receives provider-issued access/refresh credentials or, where provider APIs authorize it, programmatically generates restricted credentials. **Never assume an OAuth token can create an S3 key.**
4. Offer an optional, user-visible **Copy credential** action for a separately generated revocable credential where safe and permitted; reveal sensitive tokens only after deliberate confirmation, never by default or in telemetry/clipboard automatically. REDOWN must not invent a persistent credential for providers that only issue access/refresh tokens.
5. REDOWN automatically configures the provider connection and, after explicit Cloudflare Worker-management consent, securely installs the applicable secret into a **Worker owned by that user in their own Cloudflare account**, using the appropriate Cloudflare API. Do not install customer credentials in a shared REDOWN-owned Worker. Worker secrets are per Worker/deployment, not automatically per person: isolate customers and configurations accordingly.
6. Thereafter, the user ordinarily needs **only their Cloudflare REDOWN login** to open REDOWN, list and manage all previously authorized clouds, transfer between the resizable dual Explorer panes, and use compatible TRUE REMOTE right-click destinations. Provider refresh or reauthorization occurs as required and must be reported honestly.
7. Future **REDOWN Desktop**, offered as a native independent companion in the owner's proposed **$12.99/year bundle**, uses the same universal operation semantics and provider connections when securely authorized, but can also run independently of the browser extension. Pricing and entitlements are proposals, not shipping commitments.
8. Python CLI/developer access uses the same production Universal API and explicitly scoped, expiring sessions, not hardcoded provider secrets or an alternate untested file engine.

### Critical permission and protocol differences

| Provider | Proposed initial authorization | Credential REDOWN can use afterward | Constraint |
| --- | --- | --- | --- |
| Cloudflare R2 | Cloudflare OAuth and separately approved R2/Worker account permissions | Authorized R2 access; optional narrowly scoped R2 temporary S3 credentials | Ordinary OAuth access does not necessarily authorize creating API tokens or managing Workers; verify grant/scope and provisioning model |
| Google Drive | Provider OAuth with relevant Drive scope and offline access where supported | Provider-issued access token and, when issued, refresh token | Google Drive is not S3; do not manufacture or advertise an S3 key |
| Dropbox | Provider OAuth with selected file scopes and offline access where supported | Provider-issued access/refresh token as permitted | Dropbox is not S3 |
| Amazon S3 | Approved AWS federation/role/STS/Identity Center flow, or scoped keys if necessary | AWS temporary S3 credentials or explicitly authorized credentials | Ordinary AWS sign-in does not permit minting long-lived IAM keys |
| Backblaze B2 | Provider-supported key onboarding | Restricted application key; programmatic creation only with key-creation authority | Native B2 authorization and S3-compatible application keys are distinct |
| MEGA | Evaluate documented supported authentication and API | Provider-specific session/credentials only if allowed | Do not promise OAuth or S3 compatibility without verifying support |
| Other S3 services | Preset or custom S3 endpoint + vendor-supported setup | Scope-limited signing credentials where supported | Endpoint, region, signing, renewal, CORS and capability differences must be tested |

### Central session, renewal and persistence

- **One Cloudflare login** means one REDOWN sign-in experience for *already connected* services; it does NOT revoke, replace or bypass each provider's distinct consent and credential-lifetime policies.
- Use Cloudflare OAuth authorization-code/PKCE and supported refresh/reconnection instead of making users repeatedly log in; REDOWN may offer an optional **four-hour local access window** as a product setting, bounded by provider policy. Four hours is a REDOWN access-policy goal, not a guaranteed OAuth-token lifetime.
- Cloudflare API-token creation requires an independently adequate authorization. Never silently promote a login grant into durable admin authority, auto-create unlimited tokens, or claim that OAuth alone gives token-creation rights.
- Cloudflare management scope for Worker secret installation must be separately consented to; an R2 read/write grant by itself is insufficient. Provisioning the customer's Worker and editing its secrets are separate authorized operations. Detect missing permissions and present the minimum required step.
- Access/refresh tokens can expire, rotate, or be revoked. Implement atomic rotation where possible, least-privilege scopes, account disconnect, remote revocation when supported, auditable status, error recovery and secure reauthorization rather than silent failure.
- Customer-owned secret storage is **not zero-access cryptography**: code running in the user's Worker can access secrets. REDOWN operators must not claim they mathematically cannot access credentials without a design and audit proving that assertion. Minimize REDOWN-operated intermediaries and never log, export, transmit to analytics, or inadvertently expose secrets.
- A Worker holding multiple provider secrets raises isolation, naming, rotation and deployment-risk questions. Favor isolated per-customer Worker installations or other adequately isolated customer-owned secret storage; do not create one shared Worker with every customer's secrets.
- TRUE REMOTE depends on destination capability, authorization, source URL accessibility, execution/streaming limits and transfer cost. Automatic token setup does NOT make every website or cloud provider a viable TRUE REMOTE target.
- Keep the browser extension's ordinary flow simple: **Connect Cloudflare → Add Provider → Approve → Connected → Right-click / Browse / Drag and Drop**. No manual token copying except when the provider forces a credential setup step or the user explicitly requests export.

### Proposed implementation and acceptance (AFTER current Beta exit gates)

1. Document concrete Cloudflare OAuth/Worker ownership, management grants, local-versus-Worker secret threat model, and revocation semantics from current provider documentation. First verify whether automatic customer-Worker provisioning is practically authorized without excessive privileges.
2. Build one versioned **authorization/credential adapter** for each provider alongside its existing or future storage adapter, not a second Universal File API. Keep auth states readable: CONNECTED, REFRESHING, EXPIRED, REVOKED, ACTION REQUIRED, SCOPE DENIED.
3. Demonstrate one-time Google Drive/Dropbox consent and noninteractive access-token refresh where allowed; never mislabel these services S3.
4. Demonstrate one credential-based S3 connection, e.g. scoped Backblaze or AWS, and one authorized customer-owned Cloudflare secret installation. Test explicit denial of Worker management scopes.
5. Test credential expiration, rotation, Cloudflare logout, revoked provider consent, abandoned browser, Worker replacement, cross-account separation, extension reinstall and desktop-independent operation. Cloudflare logout must prevent new REDOWN access even if the Worker retains provider refresh credentials; define revocation and post-logout Worker exposure boundaries explicitly.
6. Validate side-by-side cloud Explorer, per-connection color identity, independently resizable panes, copy-and-verify-before-delete cross-cloud moves, and provider-specific error explanations. No claim of atomic moves.
7. Verify Python CLI can list, copy, upload, download and validate files on a time-limited scoped session with no secrets in test JSON. Benchmark the same API through real installed extension/Desktop paths.
8. Report real provider compatibility, permissions asked, refresh behavior, who operates each Worker, customer costs, measured transfer limitations and independently verified safety evidence before calling the feature production-ready.

**Non-negotiable product aim:** ONE understandable Cloudflare REDOWN login after provider onboarding, without pretending Cloudflare OAuth intrinsically creates credentials for unrelated providers. The user owns the relevant Cloudflare Worker and connected cloud accounts. REDOWN conceals unnecessary configuration while respecting every provider's authorization boundaries.

**Release policy:** This is a roadmap addendum only. Keep finishing the simple 60-exercise Test It system, independently verify Universal File API operations, then pursue programmatic testing/large-file milestones before multi-cloud authorization work. No unrelated architecture rewrite.


## IMPORTANT FUTURE ROADMAP CANDIDATE — Seamless Local Explorer and Optional Sync Companion (2026-10-28)

**Status:** RESEARCH / POSSIBLE FUTURE ROAD, NOT APPROVED IMPLEMENTATION.  
**Timing:** After R2/S3 reliability, large-file transfer validation, and multi-account/multi-cloud Explorer work. **Do not interrupt the current Beta milestones.**  
**Related:** Existing multi-cloud OAuth/customer-owned Worker addendum and proposed REDOWN Desktop bundle.

### User experience worth investigating

The owner wants REDOWN to eventually show **Local Computer + Cloud Account A + Cloud Account B** side by side, with additional provider accounts (for example, multiple Cloudflare R2 and Google Drive connections) behaving like peers inside the Universal File API. This local Explorer could make REDOWN a daily home for files otherwise scattered across local storage, Google Drive, Dropbox, OneDrive, and Save Anywhere-style workflows. This is a competitive opportunity to investigate, not a claim that REDOWN will replace those products or capture their customers.

The key question is **whether installing REDOWN's browser extension can lead to an almost effortless, trustworthy local-helper setup**, ideally one familiar installation flow rather than users manually configuring Python, PyInstaller, Native Messaging manifests, registry entries, or local services. The owner recalls a similarly seamless experience with Chute; **inspect Chute's actual installer/extension source and distribution history instead of assuming how it worked**. PyInstaller may package a helper but cannot itself let a Chrome extension silently execute an installer. Confirm browser, OS, store-policy, signature, permission, consent, uninstall, and update constraints. Never promise silent native installation or bypass security prompts.

### Compare possible architectures

1. **Extension-only local folders:** Investigate Chrome File System Access API and explicit user-selected folder permissions for browsing, previews, and manual local↔cloud transfer, subject to browser/runtime restrictions. No claim of unrestricted filesystem access or always-on watching.
2. **Extension + optional native helper:** A lightweight, signed Windows/Linux companion, potentially registered as a Native Messaging host, grants access only to explicitly authorized local directories. The extension remains the primary Explorer UI. Investigate bundled/assisted installation that feels like a single coherent REDOWN setup; verify required user execution/consent.
3. **Optional standalone desktop app:** Evaluate only if it materially improves system integration. The helper does not inherently require a separate desktop window or a second file-management engine.

### Future sync candidate

A native worker may eventually watch user-approved local folders and **automatically back up newly created or modified files** to one or multiple user-selected cloud accounts, persist resumable jobs, verify destination hashes or suitable provider evidence, and show clear per-destination status in REDOWN. Prefer **one-way backup without propagating deletions** as the initial safe mode; two-way sync, conflicts, remote deletions, recovery, encryption, offline operation, and version history require separate approval and extensive safety tests. Truly unattended sync while Chrome is closed requires a suitably installed independent background process and secure credential handling.

### Investigation gates

- Demonstrate actual extension-only local-folder access on supported browsers, including permission renewal and limitations.
- Audit Chute's historical packaging/setup path before choosing an installer strategy.
- Prototype a small authorized native helper; measure installation friction, security, privilege scope, update/uninstall cleanliness, and Windows/Linux support.
- Reuse the **same Universal File API** through a local adapter; avoid duplicating Explorer or Test It. Validate Local↔R2 Account A, Local↔R2 Account B, and R2↔R2 copies with fresh read-back, clear progress and recovery.
- Use explicit folder consent, minimal privileges, secure local-to-extension communication, scoped account credentials, and no automatic deletion of originals. Keep native installer/OS permission steps honest.
- Evaluate multi-destination automatic backup as a separate roadmap decision only after manual local/cloud transfers and large-file behavior are reliable.

**Priority rule:** This is a strategic possible path to revisit, **not a task to implement now**. Continue fixing Test It, safe live-R2 operations, S3/file-size performance, and multi-cloud account navigation first.
