# NEED TO DO — November 3, 2026
## NEW IDEA: Shelf Destinations as a familiar File Explorer, with path autocomplete and tiny save dialogs

**Status:** Proposed V3+1 user experience to review after the source-first V3 mechanical audit. **Not permission to change the existing production engine during the audit.**

**Design principle:** **Right-click to create; Shelf → Destinations to manage.** Make the interface feel like an ordinary file explorer, not a technical right-click configuration console.

### 1. Shelf → Destinations should look and work like a regular File Explorer

- Use a familiar folder-tree / file-explorer layout like the useful part of the current right-click location browser, **but remove the clutter of separate configuration buttons**.
- Allow ordinary contextual **right-click** operations on locations and shortcuts: edit path, rename menu label, add another alias, move/reorder menu entry, disable/remove shortcut. These edit the *menu configuration* only, never remote cloud files or folders.
- Put an unobtrusive **top pill / segmented selection** for **Simple | Nested | Depth**. Clicking a pill shows the saved locations and settings belonging to that presentation. In implementation, keep compatibility with **Simple** and **Nested → Narrow / Depth** semantics; in the UI, “Nested” can be the easily understood **Narrow** tree and “Depth” its own easy option.
- Show the **full exact cloud address** for each shortcut, including connection/account, bucket/container and folder path, so users can inspect or edit a destination without guessing. Display labels must never be used to infer the actual save path.
- Folder expansion must work immediately from the known tree, lazily fetching missing children on clicking the arrow. **No mandatory Browse Folders button** before expansion.

### 2. Additive editable path field with suggestions

Use a **path text field with incremental completion/autosuggestions based on actual available/indexed cloud locations**. It should be equally usable for adding a new destination or editing an existing shortcut.

Example: start entering `aes` and the UI suggests an existing directory such as `aesop`. The user chooses the match or keeps typing. Suggestions should be bounded to the exact chosen cloud connection and bucket, and distinguish same-named folders by parent path. Suggestions are not proof of current permission.

- Clicking a suggestion inserts/completes the appropriate path segment without unpredictably changing earlier segments.
- Backspace/delete naturally shortens the entered address or removes segments, allowing the user to navigate backward or revise the destination without starting over.
- Display the actual resolved path and validate exact destination identity before committing.
- Text entry must not steal focus, reload the whole editor, or silently manufacture remote folders. Preserve existing data if a lookup fails.

### 2A. Context-aware path completion: suggest *children of the current directory*

The path field must be **location-aware**, not a global text-search box. As the user types or moves the caret/backspaces among path segments, determine the currently resolved **provider connection + bucket/container + parent directory** and suggest its **immediate child directories**. For example:

```text
Cloudflare / photos / Photography /
  ├─ Portraits/
  ├─ Landscapes/
  └─ Weddings/

User selects Portraits/:

Cloudflare / photos / Photography / Portraits /
  ├─ Clients/
  └─ Personal/
```

When the user types a partial final segment such as `Por`, narrow the candidates to `Portraits/` under **Photography**, not similarly named folders elsewhere. Selecting a suggestion completes **only the active segment** and updates the parent context for subsequent suggestions. A backspace or deletion that goes up one level immediately returns to that parent's actual children. Full-address display stays synchronized with the resolved canonical destination.

- Prefer already indexed/cached child locations for immediate suggestions, then automatically perform a bounded, paginated child listing when needed. No prerequisite **Browse Folders** click or exhaustive provider scan.
- Suggestions are scoped to the exact cloud connection, bucket and parent path; identical names in different directories are never conflated.
- Clearly distinguish **loaded**, **loading**, **empty**, **partially loaded**, **stale**, and **permission denied** states. An absent suggestion is not proof the child does not exist.
- Support mouse and keyboard selection (Up/Down/Enter/Escape), keep input focus stable, preserve editable text, and safely handle fast typing and stale asynchronous responses.
- Only known/resolved locations can be committed as an exact save destination; typing an invented path must not silently create remote folders or authorize a save. Let the user revise the text naturally, without wiping their draft.
- The child-directory lookup is a navigation/autocomplete feature shared by Simple and Narrow; it must not modify the mode's saved shortcuts, aliases or native menu until the user intentionally saves.

**IF** a resolved path ends in a folder separator, **THEN** suggest its known immediate child directories. **IF** the user types characters in the next segment, **THEN** filter only those siblings. **IF** the user deletes a segment to move upward, **THEN** show that parent directory's children again. **IF** the cache lacks a complete listing, **THEN** fetch that level lazily and report its true coverage.

### 2B. Clickable path chips + visually distinct child and sibling suggestions (NO TYPING REQUIRED)

**Owner refinement:** Make the path editor a familiar sequence of small clickable folder tags/chips. Immediately underneath, show *children* and *siblings* as tap/clickable suggestions in two clearly separated visual styles (possibly different theme-appropriate colors). A user should be able to build, change, and save a complete destination **entirely by clicking**, without typing even one character. Typed path autocomplete stays optional for power users.

```text
Current location: [Cloudflare] / [photos] / [Photography] / [Portraits]

CHILDREN ↓   (add the next path segment)
  [Clients/]    [Personal/]

SIBLINGS ↔   (replace the current final segment)
  [Weddings/]   [Landscapes/]   [Street/]

Click [Photography] to go up and choose one of its children.
```

- **Click a child:** append that exact directory to the current path and reveal its own immediate children and siblings.
- **Click a sibling:** replace the current folder with that sibling, removing any descendants that no longer belong to the selected path. This only alters the draft, not an already saved shortcut; offer Undo for an accidental click.
- **Click an earlier chip:** focus/navigate back to that ancestor and suggest its immediate children, enabling effortless movement backward and down another branch.
- **Click the bucket/account chip:** return to its authorized root locations; do not confuse similarly named buckets across connections.
- **Typing is OPTIONAL:** users who prefer a keyboard can type partial segments and select completions, but there is no separate required Browse Folders button, hidden prerequisite, or need to remember slash-separated paths.
- **Suggestions are based on actual resolved location identities:** cached/indexed children appear quickly; if missing, lazily request bounded child listings automatically. Show loading, empty, stale, partial, and permission-denied states truthfully. Never invent directories because a user clicks a chip.
- **Differentiate children and siblings by both labels/icons AND color:** remain readable for color-blind users and across Porcelain, Midnight and Neon themes; use keyboard focus and accessible controls.
- **Only Save/Apply commits destination edits:** clicking chips changes the path preview/draft; it never silently creates a shortcut, new cloud directory, or remote upload. Existing native save entries stay intact until the user confirms the change.

**IF** a user does not want to type, **THEN** they can pick child/sibling chips all the way to their destination. **IF** they choose a child, **THEN** append it. **IF** they choose a sibling, **THEN** replace the active directory, not append it. **IF** they choose an ancestor chip, **THEN** navigate upward and display the appropriate children.

### 2C. FINAL SHELF NAVIGATOR LAYOUT: editable path + THREE horizontally scrollable pill rows

**Owner's latest clarified design:** Directly beneath a single editable, autocomplete-enabled full-location field, display **three immediately visible rows** of clickable folder pills. Each row may contain more choices than fit the Shelf; therefore **each row gets its own horizontal scrolling** (trackpad/swipe/mouse and unobtrusive scroll controls), without making the whole Shelf page jump. Three rows are **Parents**, **Siblings**, and **Children**. Typing and clicking are equally valid alternatives; neither requires a traditional expanded tree or a separate **Browse Folders** operation.

```text
Destination: [ Cloudflare / photos / Photography / Portraits /       ]  ← type or click

PARENTS   ← [photos] [Photography]                        →
SIBLINGS  ← [Landscapes] [Weddings] [Street] [...]         →
CHILDREN  ← [Clients] [Personal] [Favorites] [...]         →
```

- **Parents**: the exact resolved ancestor chain, each ancestor as a pill. Clicking `Photography` navigates up to that directory and re-evaluates all three rows. The current breadcrumb/path field also remains clickable/editable.
- **Siblings**: the other immediate directories under the current location's parent. Clicking `Weddings` **replaces the active final directory** (and drops incompatible deeper segments from the draft) rather than appending `Weddings` underneath `Portraits`.
- **Children**: the current directory's immediate children. Clicking `Clients` **appends that folder** to the draft path and refreshes all three rows in place.
- **Editable full-address field**: entering `.../Por` suggests immediate child matches such as `Portraits` from the resolved `Photography` parent. Accepting an autocomplete option updates the same underlying path state as clicking a pill. Backspace, clicking a parent, or selecting a sibling changes the suggestion scope immediately.
- **One canonical draft**: field text, displayed breadcrumb pills, the active resolved location, and all three rows must stay synchronized, even after an asynchronous refresh or rapid navigation. A pill click is preview/navigation only; commit only on the user's explicit Save/Apply.
- **Row usability**: keep the section labels permanently visible and distinguish the three pill categories by complementary theme colors *and* text/icons, not color alone. Use bounded independent horizontal scrolling with obvious more-items affordances, keyboard focus/navigation and screen-reader labels. No unbounded vertical row growth.
- **Data safety**: suggestion lists come from actual connection-scoped folder identities and cached or lazily fetched directory children. Indicate loading, partial, empty, stale and denied status; never merge identical folder names from different cloud locations; never infer write permission merely from a suggestion.
- **Small Shelf compatibility**: compact pill sizes and independent row scrolling preserve the limited Shelf height, while a larger Shelf can display more choices without changing the mechanics.

**IF** the user types, **THEN** autocomplete supplies the valid next segment. **IF** the user clicks a parent, **THEN** navigate up. **IF** the user clicks a sibling, **THEN** replace the current segment. **IF** the user clicks a child, **THEN** descend one level. In every case, the path field and three pill rows refresh together.

This three-row pill navigator supersedes any interpretation that suggestions must be hidden in a dropdown, shown only when typing, or offered only as two categories. Treat it as the preferred UX candidate for the future V3+1 Shelf destination editor; do **not** build it during the current documentation-only audit.

### 3. Quick save/confirm interaction for a selected location

After selecting or editing a destination and pressing **Save** (saving the **menu configuration**, not uploading a file), use a small, intelligible flow:

1. **“Keep as Simple, with menu label: [______]?” — Yes / No.**
2. **Yes**: store the exact destination as an independently identified flat **Simple** save shortcut, using the entered label or sensible existing/bottom-folder/bucket-name fallback.
3. **No**: proceed to **Narrow (Nested)** configuration for that same selected location. Show the natural cloud bucket/folder ancestry with **two editable columns**, e.g. **Actual folder/directory name | Menu label**. The user may optionally rename *the displayed menu labels* at each level. An untouched label uses the actual folder/directory name; no remote rename or unnecessary override is recorded.
4. Confirm and save the desired menu arrangement, generating navigation-only ancestors and exact selected save actions as required. The resulting native menu should follow actual path hierarchy; parent save targets with children need a separate Save here action.

The **No** in the “Keep as Simple?” question means **use Narrow**, *not* “cancel the destination” or “delete the shortcut.” Distinguish this from the earlier one-time-save flow, where a separate **“Remember this destination? Yes/No”** decision may be used.

### 4. Handle duplicates without alarming the user

If another shortcut already references the same exact location or the new visible label collides with an existing entry at the relevant menu level, gently ask:

**“Already exists. Use anyway?” — Yes / No**

- **Yes** explicitly creates/keeps another independent menu shortcut or presentation alias; same actual folder can appear multiple times with distinct stable menu-entry IDs.
- **No** lets the user edit the label or choose a different entry, without silently deleting, merging or changing the original.
- Check exact identity *and* potentially confusing displayed labels separately. Two names that look alike are not necessarily the same location; two different labels may target exactly the same location. The warning can clarify which applies.
- Shared ancestors in Narrow are normally displayed once; paths differing only in the final one or two levels branch naturally. A user-created alternate full named branch requires a separately identified branch instance, not a duplicated remote folder.
- A successful menu edit should show **Saved** only after local persistence; distinguish **Applied to Chrome** until native registration is actually acknowledged. Never claim verified upload completion from menu configuration alone.

### 5. DEPTH IS DELIBERATELY MUCH SIMPLER

**Owner clarification: Depth should simply show the available buckets, let the user check the buckets they want, then choose the depth. EASY.**

The Depth view should contain only what the user needs:
1. **Buckets:** a clear checklist of the buckets/containers actually available to the selected supported provider connection.
2. **Depth:** one simple selector for the level, **1–10** (or expanded range only by later explicit decision).
3. **Save / Apply:** commit that provider's participating buckets and selected depth, show clear pending/completed state.

**That's it. No manual destination-label editor, no adding folder paths one by one, and no separate Browse Folders ritual.** V3+1 does the automatic bounded discovery/known-hierarchy projection behind the scenes; a partial inventory must be reported honestly. The bucket root is level 0, first child folder level 1, etc. Selecting Depth should never mutate Simple/Narrow saved aliases or delete previously known deeper folder inventory.

### 6. Simple rules

- **IF** the user picks **Simple** in the top pill, **THEN** show flat saved shortcuts with their complete underlying locations and menu labels, editable in place.
- **IF** the user picks **Nested**, **THEN** show the curated paths and labels, with the same folder browsing and path-entry controls but a genuinely nested menu result.
- **IF** the user picks **Depth**, **THEN** show bucket checkboxes and a numeric depth selector, not another folder editor.
- **IF** the entered menu label/location conflicts with another entry, **THEN** ask **“Already exists. Use anyway?”**; respect the answer and preserve distinct stable IDs.

### 7. Architecture / sequencing guardrails

The Shelf editor, contextual creation popup and native menu must work through the same provider-owned canonical destination/shortcut configuration and one narrow shared Chrome menu-registration boundary, not competing menu engines. For S3-compatible connections, future V3+1 should support sibling S3 providers through adapters. Google Drive, Dropbox and OneDrive remain independent of V3 internals while sharing the same familiar menu presentation *conventions* and the common registrar only.

This is **a future UX proposal to compare with the ACTUAL code** in the ongoing source-first audit. Document current implementation, mismatches, collision mechanics and migration needs; **do not remove the present UI or build these interactions in the documentation run**.
