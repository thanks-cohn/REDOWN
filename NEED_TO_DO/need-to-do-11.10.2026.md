# NEED TO DO — 11.10.2026 — REDOWN History, Shelf and browser-file future
**Owner direction:** November 10, 2026. This file records the full requested scope. As separately authorized later, implementation of the Guarantee Drag and Drops queue and signed-out Explorer stability has begun **only on the isolated feature branch**; other listed features and the new P0 multi-cloud regression remain unverified, not claims of completion.

## Scope, feasibility and required construction

**Why this is possible:** Existing REDOWN History uses IndexedDB and already records transfer metadata; existing Chutey has working reference drag/drop pathways, and REDOWN has a Shelf, providers, previews, navigation and an in-development transfer engine. This does **not** mean cross-site file drops or persistent transfers already work in REDOWN.

**Needed first:** (a) search metadata/index/parser/paginated query API, (b) permissioned transfer bridge with real byte streaming and provider receipts, (c) durable click/transfer queue and independently executing worker/companion when page/tab closes, (d) separate immediate visual acknowledgement vs verified completion. Determine actual MV3/site constraints with live acceptance tests; do not promise page-independent transfers for pages that require transient in-tab credentials.

## Vision
Treat History and FILES as usable browser-native file surfaces, not static receipts. A person can revisit, find, locate, pick up and send real files from cloud folders to the web, and can capture website files directly into selected folders. REDOWN's Shelf is a working space; Chutey is the reference for real bidirectional browser/file dragging. Follow existing REDOWN Universal File API / GUI-to-API parity, verified transfer receipts and permission boundaries.

### P1 — Real Chutey-parity drag-and-drop: web ↔ Shelf / cloud Explorer

**November 10 owner clarification — CLOUD ↔ WEBSITE, URL/pointer first, NOT local-file transfer.** The primary flow is remote cloud object → website and website image URL → chosen cloud folder. Do not insert an unnecessary local filesystem save or require the Chutey Windows native companion as a default prerequisite. Prefer (1) direct, appropriately authorized URL/pointer handoff where the receiving website supports image/file URL imports (Google Lens documents a "Paste image link" input), then (2) short-lived scoped cloud/Worker URL serving the exact selected object when an ordinary provider link is inaccessible and user explicitly initiates the transfer, then (3) ephemeral in-memory byte streaming into a supported website file drop/upload path where the website does NOT ingest URLs as uploaded files (ChatGPT's documented attachment flow supports actual files). No disk writes should be necessary for this core remote-to-web handoff. A URL placed into a text prompt must never be represented as a successfully attached file. Chutey is a UX/transfer compatibility reference, not a compulsory installation.

**Remaining real constraints (not objections to feasibility):** a private cloud object cannot be fetched by a third-party service from an OAuth-protected Drive/Dropbox/OneDrive URL without authorization; a temporary scoped access URL may be needed. A public URL must be treated as deliberate disclosure to the receiving site and must expire/revoke when feasible. Browsers restrict cross-origin reads and synthetic drag/drop, and Google, Yandex, ChatGPT and other destinations each determine which URL and File inputs they actually accept. A Worker can securely fetch/stream bytes without storing a local file, but cannot force an uncooperative website to treat a string pointer as an attached upload. Test each target in the installed browser and adapt without claiming universal drag support.
1. **Website → folder:** drag an image/file from a webpage (e.g., Google image results) into a concrete REDOWN cloud folder/destination, or select the folder then drop into Explorer. The destination is determined by the *actual target folder*, not a global default or a thumbnail alone. Create a queued receipt; validate sender, bytes/source and destination; remote vs browser-byte transfer follows provider policy. Ask permission if required. Show success only after provider-verification.
2. **Cloud folder → website:** select one or many real saved files in REDOWN FILES/History and send them to Google image search, Yandex, ChatGPT and other supported websites. **First try a URL/pointer path when the site accepts it** (for example Google Lens's image-link input). For private objects, use a narrowly scoped short-lived Worker-served object URL with actual access validation and revocation rather than leaking cloud OAuth tokens. If a website requires a real file rather than a link, stream/decode bytes into a memory-backed File/drop or the website's supported upload flow; no local disk is required. Preserve filenames/MIME types and explicit user action. Chutey native companion is optional for other desktop/cross-browser integration, not a prerequisite to this remote cloud-to-website feature. Verify behavior for each target; never claim a pasted link is a completed file attachment.
3. **Bidirectional where possible:** copy/drag files between the Shelf and pages. Include keyboard/copy/paste fallback when browser cross-extension/cross-origin restrictions prevent trusted drag. Reuse the existing permissioned adapter/Universal File API, not Chute's private opaque IDs or localhost URLs as unverified public download URLs. Chutey and REDOWN have distinct security authority; cross-extension transfer requires deliberate handoff.
5. **API parity:** `drag.inspect / drag.receive / drag.prepare / drag.commit / drag.cancel / drag.receipt` (illustrative) must be available with the same semantics programmatically and through GUI.
6. Acceptance requires true browser-to-cloud folder import; real cloud-to-Google/Yandex/ChatGPT file bytes; round-trip where supported; verified provider receipt; no leaked source/page URLs in provider storage; denied permission/expired credentials fail correctly and retain actionable recovery. Do not conflate mock drag events with live site acceptance.

## November 10 addition — "Guarantee Drag and Drops" remote-first fallback (OWNER REQUEST; design only)

**User goal:** Give people a Settings opt-in called **"Guarantee Drag and Drops"** so dragging website ↔ REDOWN cloud folders or REDOWN cloud files ↔ compatible websites uses **all permitted delivery methods**, falling back automatically when a fully remote exchange fails. Preserve the ambition of universal-feeling drag and drop while not promising that every independent website accepts programmatic drops. This setting does not exist yet. No runtime code is authorized by this note.

### Intended decision order — same user gesture, no repeated manual setup
1. **Fully remote first (preferred, no browser storage):** website URL → REDOWN Cloudflare Worker fetch → verified cloud folder, or REDOWN cloud object → authenticated Worker / short-lived object URL → receiving website's supported URL ingestion endpoint. Where the destination provides an authorized upload API, Worker may stream the actual bytes directly to that API. Keep destination credentials scoped, do not expose OAuth tokens or page/source URLs to cloud storage providers. A Worker can stream gigabytes without buffering the entire object into Worker memory; the receiving service must, however, support the upload/URL protocol and user authorization.
2. **Memory-backed browser-byte fallback:** if direct URL/API handoff is unsupported, request the object through authenticated REDOWN/Worker access, acquire real bytes in the browser (a `Blob`/`File` or chunks) and hand them to the compatible website's file-drop or upload interface. Reverse flow: if Worker cannot fetch a web image because the content only exists in a permitted browser session, capture permitted bytes in the browser and upload to the chosen cloud folder with a verified receipt. **Memory-backed is not necessarily a disk download**; browser memory and site APIs may constrain file size. Never infer website acceptance from merely dispatching a synthetic drop event.
3. **Opt-in temporary browser-storage fallback:** only when staging materially improves reliability/size, use bounded private browser storage (IndexedDB / Origin Private File System where supported) with a configured byte budget, quota preflight, cleanup and explicit retention controls. Temporary storage uses the user's computer, not a traditional Downloads-folder file. Do not store credentials alongside cached bytes, do not persist source/page URLs to providers, and automatically clean cache on completed/cancelled transfers unless a separately authorized retry policy needs it.
4. **If all paths fail:** never fake success. Show a useful reason such as `Website doesn't support this drop`, `Authorization needed`, `Insufficient browser storage`, `File too large for safe browser staging`, or `Transfer interrupted`, with Retry/Copy link/Open destination/manual upload fallback where feasible. Real success means the receiving provider/website actually accepted the handoff, with verified cloud receipt where REDOWN controls the destination.

### Settings UI contract (not implemented)

- **Toggle label requested by owner:** `Guarantee Drag and Drops`.
- **Suggested default:** OFF (remote-only by default; avoid unexpected browser cache use). ON explicitly authorizes automatic browser-byte fallback for browser-to-website/cloud file handoffs after a remote attempt fails.
- **Suggested accompanying text:**
  > First try direct cloud-to-website transfers. When a website cannot accept a remote link, REDOWN can temporarily use browser memory or storage to deliver the file. This may use space on your device. We recommend at least 1 GB of free space for larger files; actual space needed depends on file size, browser quotas and transfer method. Temporary files are removed after successful handoff or expiry.
- **Precise promise:** `Guarantee` is the **owner's desired name** for an aggressive reliability mode, **not** a technical promise of universal acceptance, because some third-party websites require trusted gestures, reject synthetic drags or lack usable upload endpoints. The interface should disclose `Works on supported sites; certain sites may require manual upload` rather than claiming universal compatibility. Show `Remote`, `Browser memory` or `Temporary browser storage` as the actual method used.
- Let user view and configure maximum temporary bytes, inspect current use, clear cache now and select no-cache behavior. Check actual availability via `navigator.storage.estimate()` and a write attempt, because estimates/quotas are not a guaranteed reservation; fail safely on `QuotaExceededError`. **1 GB is a recommendation**, not a required allocation, browser quota guarantee or forced storage reservation. Do not pre-allocate 1 GB.
- Clear sensitive temporary bytes on cancellation or expiry, avoid lingering object URLs, prevent unauthorized cross-site access, bound concurrent transfers and staging. Do not let the fallback bypass user permissions, provider OAuth scope checks or destination authorization.

### Distinguish inbound save policy from outbound handoff policy

REDOWN's default Cloudflare R2 **TRUE REMOTE right-click save** must remain Worker-fetch, with NO silent browser-byte fallback. The opt-in `Guarantee Drag and Drops` mode is a separate **user-authorized drag/import/export transport preference**. If dragging from website to R2 would otherwise fall back to browser bytes, make the mode choice and disclosure explicit; do not silently mutate the default TRUE REMOTE preference or falsely label such a transfer remote. Outbound cloud → website may stage bytes in the browser when expressly enabled, with no implication that Cloudflare stored files locally.

### Engineering and acceptance gates

- Define a versioned `handoff.plan/prepare/transfer/verify/cleanup` API (illustrative names) with deterministic method selection, `remote_url` → `browser_memory` → `browser_cache` fallback reason and cleanup receipts. GUI calls that API; one engine drives animation, queue and actual transfer state.
- Test direct URL success, a website that rejects URLs but accepts actual file bytes, website that rejects synthetic drops, private R2 object access with short-lived read token, Google Drive/Dropbox/OneDrive OAuth expiration, unsupported origins, Google/Yandex/ChatGPT per-site behavior, large files, low-memory and storage-quota failure, tab close and restart, cancellation and cleanup.
- For website destinations, record observable accepted/failed state only to the extent actually available; do not invent third-party upload confirmation. For REDOWN cloud destinations use independent provider verification before `SUCCESS!`.
- Cloudflare reference: Workers Streams API supports pass-through streaming; R2 S3 presigned GET URLs may provide time-limited single-object reads, but signed links act as bearer tokens and must be short-lived and shared only after explicit action. Worker cannot push file bytes into an arbitrary website's page without a cooperating URL/API/file-input path. Chrome's MV3 worker can suspend; a browser staging operation needs lifecycle-safe state and true resume limits.
