# NEED TO DO — 11.10.2026 — REDOWN History, Shelf and browser-file future
**Owner direction:** November 10, 2026. **Documentation only. Do not implement or modify runtime source on the strength of this file.** All requested features below are aspirations/requirements, not claims of completed or tested functionality.

## Scope, feasibility and required construction

**Why this is possible:** Existing REDOWN History uses IndexedDB and already records transfer metadata; existing Chutey has working reference drag/drop pathways, and REDOWN has a Shelf, providers, previews, navigation and an in-development transfer engine. This does **not** mean cross-site file drops or persistent transfers already work in REDOWN.

**Needed first:** (a) search metadata/index/parser/paginated query API, (b) permissioned transfer bridge with real byte streaming and provider receipts, (c) durable click/transfer queue and independently executing worker/companion when page/tab closes, (d) separate immediate visual acknowledgement vs verified completion. Determine actual MV3/site constraints with live acceptance tests; do not promise page-independent transfers for pages that require transient in-tab credentials.

## Vision
Treat History and FILES as usable browser-native file surfaces, not static receipts. A person can revisit, find, locate, pick up and send real files from cloud folders to the web, and can capture website files directly into selected folders. REDOWN's Shelf is a working space; Chutey is the reference for real bidirectional browser/file dragging. Follow existing REDOWN Universal File API / GUI-to-API parity, verified transfer receipts and permission boundaries.

### P1 — Searchable History, page-local by default, global on command
1. Put a persistent, keyboard-accessible **search field above History results**. Typing ordinary text filters only the **currently selected page's 40-ish records**, without silently shifting the archive/page or making network requests. Preserve the page index; show an honest filtered count and a clear/empty state.
2. Command grammar (case-insensitive commands/hostnames, preserve literal user text):
   - `funny downtown cop story` — plain local page search in recorded filename, description/text metadata where present, recorded source/hosting URLs and saved destination path.
   - `search:all funny downtown cop story` — search **the full locally indexed History archive**, not only one page, with its **own paginated results**.
   - `search:hitomi.la funny downtown cop story` — full-archive search restricted to recorded entries whose original hosting-page/source hostname is **hitomi.la or a subdomain**, plus the text query.
   - `search:google.com romance` — full-archive search restricted to the recorded Google domain and matching text.
   - `search:hitomi.la tag:age romance` — host restriction AND exact stored `age` tag AND text `romance`; comma-separated tags may be supported as explicit OR groups only when visibly documented.
   - Support `search:all search:hitomi.la tag:age "funny downtown cop story"` with a quoted exact phrase; independent terms are AND, case-insensitive. Whitespace only should reset search.
3. Search commands are **local filters against the user's own records**, NOT searches of third-party websites. `tag:name` only matches an actual stored tag/token; don't infer tags from the image or scrape sites to invent them. If older records lack tags, show the limitation rather than pretending all contents are indexed.
4. Parse safely: don't execute or treat query text as URLs, regex, HTML, SQL or network requests; don't embed arbitrary hostname in provider API calls. A `search:host` token is a *hostname filter*, exact/subdomain only; prevent `notgoogle.com` matching `google.com`. Invalid command text yields a clear validation message.
5. Results preserve History's verified GO TO, previews, More, URL provenance and page navigation; search page changes auto-expand the newest date path as above. Search across all records must use a bounded/cancellable **IndexedDB query API** with stable sort and cursor pagination rather than loading all image bytes or materializing the entire archive into DOM. Metadata-only indexing. Handle storage limits, stale queries and storage errors honestly.
6. **API-first:** specify `history.search({scope:'page'|'all',page,query,host,tags,cursor,limit})` and `history.parseQuery(text)` (names illustrative; align with existing Universal File API authority), with deterministic schema/error outcomes. GUI calls the same search API. Don't create a second shadow History store.

### P1 — Real Chutey-parity drag-and-drop: web ↔ Shelf / cloud Explorer

**November 10 owner clarification — CLOUD ↔ WEBSITE, URL/pointer first, NOT local-file transfer.** The primary flow is remote cloud object → website and website image URL → chosen cloud folder. Do not insert an unnecessary local filesystem save or require the Chutey Windows native companion as a default prerequisite. Prefer (1) direct, appropriately authorized URL/pointer handoff where the receiving website supports image/file URL imports (Google Lens documents a "Paste image link" input), then (2) short-lived scoped cloud/Worker URL serving the exact selected object when an ordinary provider link is inaccessible and user explicitly initiates the transfer, then (3) ephemeral in-memory byte streaming into a supported website file drop/upload path where the website does NOT ingest URLs as uploaded files (ChatGPT's documented attachment flow supports actual files). No disk writes should be necessary for this core remote-to-web handoff. A URL placed into a text prompt must never be represented as a successfully attached file. Chutey is a UX/transfer compatibility reference, not a compulsory installation.

**Remaining real constraints (not objections to feasibility):** a private cloud object cannot be fetched by a third-party service from an OAuth-protected Drive/Dropbox/OneDrive URL without authorization; a temporary scoped access URL may be needed. A public URL must be treated as deliberate disclosure to the receiving site and must expire/revoke when feasible. Browsers restrict cross-origin reads and synthetic drag/drop, and Google, Yandex, ChatGPT and other destinations each determine which URL and File inputs they actually accept. A Worker can securely fetch/stream bytes without storing a local file, but cannot force an uncooperative website to treat a string pointer as an attached upload. Test each target in the installed browser and adapt without claiming universal drag support.
1. **Website → folder:** drag an image/file from a webpage (e.g., Google image results) into a concrete REDOWN cloud folder/destination, or select the folder then drop into Explorer. The destination is determined by the *actual target folder*, not a global default or a thumbnail alone. Create a queued receipt; validate sender, bytes/source and destination; remote vs browser-byte transfer follows provider policy. Ask permission if required. Show success only after provider-verification.
2. **Cloud folder → website:** select one or many real saved files in REDOWN FILES/History and send them to Google image search, Yandex, ChatGPT and other supported websites. **First try a URL/pointer path when the site accepts it** (for example Google Lens's image-link input). For private objects, use a narrowly scoped short-lived Worker-served object URL with actual access validation and revocation rather than leaking cloud OAuth tokens. If a website requires a real file rather than a link, stream/decode bytes into a memory-backed File/drop or the website's supported upload flow; no local disk is required. Preserve filenames/MIME types and explicit user action. Chutey native companion is optional for other desktop/cross-browser integration, not a prerequisite to this remote cloud-to-website feature. Verify behavior for each target; never claim a pasted link is a completed file attachment.
3. **Bidirectional where possible:** copy/drag files between the Shelf and pages. Include keyboard/copy/paste fallback when browser cross-extension/cross-origin restrictions prevent trusted drag. Handle multiple files, large files, cancellation, inaccessible private clouds, external-session expiry and storage quotas.
4. **Reference implementation:** `thanks-cohn/chute` `extension/drag-relay.js`, `extension/direct-drop-google-yandex.js`, `extension/explorer-view.js`, plus REDOWN `extension/chute-stage.js`, `docs/shelf-chute-integration/`. Reuse the existing permissioned adapter/Universal File API, not Chute's private opaque IDs or localhost URLs as unverified public download URLs. Chutey and REDOWN have distinct security authority; cross-extension transfer requires deliberate handoff.
5. **API parity:** `drag.inspect / drag.receive / drag.prepare / drag.commit / drag.cancel / drag.receipt` (illustrative) must be available with the same semantics programmatically and through GUI.
6. Acceptance requires true browser-to-cloud folder import; real cloud-to-Google/Yandex/ChatGPT file bytes; round-trip where supported; verified provider receipt; no leaked source/page URLs in provider storage; denied permission/expired credentials fail correctly and retain actionable recovery. Do not conflate mock drag events with live site acceptance.

### P1 — Instant click-orb + real per-card progress
1. Start the small click/light-orb **at the first user action/next paint** in the available UI; do not wait for `chrome.tabs.query`, remote discovery, OAuth, provider readiness, network response, or a promise chain before showing immediate **acknowledgement**. The origin-page/extension context can render an instant local pulse; synchronized Shelf/provider-card arrival may follow asynchronously. Avoid duplicate orb/replays.
2. Each destination card has a quiet loading state animation for actual queued/preparing/fetching/uploading/verifying stages, with meaningful progress where measurable. Hover/keyboard/status text exposes state. Throttle updates, avoid excessive layout shift, respect reduced motion, and stop or turn to recoverable error on failure.
3. **Acknowledged click ≠ saved**. Only an independently confirmed provider commit/HEAD/receipt triggers `SUCCESS!`, the verified save sound, counters and History success. A failed/rejected/no-login action must never celebrate. No arbitrary timer means success. Existing `extension/shelf-click-feedback.js` currently waits on a window promise and `chrome.tabs.query` before `arrive(event)`; fix the first-click UX without weakening sender/window validation for delayed cross-context events.
4. API-first state machine: `clicked → queued → preparing → transferring → verifying → verified`, plus `requires-auth / retryable / failed / cancelled`. Every state has a monotonic event ID, is inspectable and testable.

### P1 — Persistent click/transfer queue
1. Add compact **Recent Clicks / Queue** to Shelf, newest first, as far back as reasonably supported by **local storage quota and user retention settings**. Every intent is written durably *before* initiating transfer; separate History verified outcomes from click attempts. No fabricated past clicks.
2. Queue entry: stable ID, click time, provider, intended bucket/folder/account, filename/type/size when known, status, retries, request metadata needed to resume and a pointer to a *permitted* source. Store recorded page/source URLs locally only when needed for recovery/History; **never send page/source URLs to cloud providers**, only uploaded file bytes and filename/extension (and necessary object destination metadata). Redact credentials, avoid logging sensitive page addresses. User may clear entries and cached bytes independently.
3. **Continue after leaving the originating webpage**: transfer ownership must move from the tab into a durable extension/background or independently executing remote worker/native companion at enqueue time. Closing the original tab cannot cancel valid jobs. Chrome MV3 service workers can suspend and the browser can close; use persistent job state, bounded resumable/retry logic and the actual execution environment. **Do not promise uninterrupted background transfer across browser shutdown** unless a real autonomous worker/native component backs it. No duplicate saves: idempotency keys, exact destination reconciliation and independently verified receipts.
4. Preserve failed/auth-required entries so a user can reconnect and retry a pending save instead of re-finding an image. A remote URL with expired credentials or transient page-only access is not magically fetchable later: retain failure + link/context and a manual retry option, or opt-in byte cache subject to quotas, MIME and safety policy. Never auto-download arbitrary private content without explicit consent.
5. Immediate queue card + progressive state, cancellation, Retry, clear/completed retention, deduplication and fair scheduling. Support page/restart recovery tests, provider errors, permissions, duplicate filenames KEEP BOTH, and no false success. Existing History IndexedDB archive is **not** a substitute for pending-work ownership; existing Chute temporary staging (`redown-chute-v1` TTL) is **not** a durable queue.

## Cross-cutting non-negotiables
- **Privacy:** provider APIs receive only upload bytes + file name/extension and required destination identifiers; never source URL, parent page URL, raw auth tokens, Chutey local file paths or debug payloads.
- **Authentication:** logged-in card ≠ operational saving readiness. Check live provider scopes/permissions and repair the precise missing authorization while preserving queue intent.
- **TRUE REMOTE:** Cloudflare R2 saves must remain Worker-fetch with no browser-disk dependency; no silent fallback to browser-byte transfer. For other providers follow their explicit mode policy and confirmed capabilities.
- **One engine / GUI ↔ API parity:** no duplicated behavior paths, no fake success/ready/bytes; tests prove state and operations, not just written instructions.
- **Test gates:** unit grammar and cursor pagination; page-first expansion; negative GO TO eligibility; rapid-click pulse without duplicated receipts; tab-close continuation; service worker restart; provider reconnect; no unauthorized provider call; real Chromium and Google/Yandex/ChatGPT compatibility where platform allows. Record results separately from simulated passes.
- Existing preview Free/Premium entitlement gates remain. Existing History is user-owned; search and retention must not silently delete it.
