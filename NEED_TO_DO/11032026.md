# NEED TO DO — November 3, 2026

## IMPORTANT NEW IDEA: RIGHT-CLICK TO CREATE, SHELF TO MANAGE

**Status:** Owner-proposed V3+1 experience, for review and future implementation. **Do not change the existing V3 during the current source-first audit.**

### Core product decision

Eliminate the complex standalone **Right-Click Setup** section from the normal REDOWN user experience. REDOWN should build its native Chrome right-click destinations naturally while people use it. The **Shelf → Destinations** area becomes the central, intuitive place to manage and reorganize those destinations.

**Guiding sentence: Right-click to create. Shelf to manage. V3+1 handles the machinery.**

### Creating a destination through ordinary use

1. User right-clicks a supported web object and chooses REDOWN, then a connected cloud and an exact save location using an immediately navigable folder picker. Account/bucket roots must be visible or transparently loading, and folder arrows must lazy-load children without pressing **Browse Folders** first.
2. If the chosen location is not already a saved shortcut, the compact popup asks whether to **add this location to the right-click menu: Yes / No**. A **No** means save once to the exact chosen location without creating a permanent menu shortcut.
3. A **Yes** offers **Simple**, **Narrow**, or **Both**. Simple creates a flat named save shortcut. Narrow creates a save shortcut arranged under its actual selected folder ancestry. Both adds independent entries to both configurations.
4. An optional Menu Label can default to the **bottom folder name** or **bucket name** (bucket root uses bucket name), or be custom. Changing this label never renames a real cloud folder or changes the exact destination identity.
5. The save must use existing verified save transport and exact route resolution. Creating a shortcut must not silently create cloud folders, perform a second upload, or invent an authorization.

**Existing configured destination:** One native right-click click saves directly. No popup, extra confirmation, repeat login or menu-design ceremony.

**New or ad hoc destination:** Choose location → save once → optionally remember it. Keep the save flow obvious and quick. The popup should be contextual, not an interruption on every save.

### Shelf → Destinations: the natural management home

Place the lightweight destination manager **inside the existing Shelf** under **Destinations**, not in another sprawling Right-Click Setup page.

The Shelf manager should let the user:
- See saved destination shortcuts by connected provider and mode.
- Rename menu labels without renaming real folders.
- Reorder, disable and remove menu entries without touching cloud objects.
- Create additional aliases pointing to the same exact cloud location.
- Inspect/edit how a target appears in Simple or Narrow, with each mode's configuration protected from accidental overwrites.
- Choose Depth for capable providers through a small **participating buckets + depth 1–10** control, rather than requiring a second manually constructed folder tree.
- Preview the resulting native menu and see truthful persisted/pending/Chrome-acknowledged Apply states.

Preserve provider-local defaults and native menu ordering where already required by owner contracts; especially distinguish provider **Home = exact default SAVE** from **REDOWN Go Home = open/navigate dashboard**.

### How duplicates and branches behave

**A real cloud location, a shortcut to it, and a rendered menu branch are three different identities.**

- Two paths sharing ancestors (including paths differing only in the last one or two folders) reuse their common *visual* ancestry in Narrow and diverge only where they differ.
- The same exact destination may have multiple independently named shortcuts (e.g. **Client Photos**, **My Portraits**). Their IDs differ, but both resolve to one exact real destination; one click triggers one save.
- If a selected parent also has selected descendants, the parent remains a navigational submenu, with an explicit **Save here** action for its separately approved target.
- An ancestor shown solely to navigate is **not** automatically an approved save location.
- A contextual **Add another menu entry** allows a second or third alias. An optional advanced **Add alternate branch** later allows two independently named full visual routes to the same exact destination; do not automatically clone full trees for ordinary aliases.
- Duplicate visible labels should be flagged for clarity but never merged, routed or authorized by display text.

### The internal architecture still matters

Do not replace the underlying right-click engine with a popup-specific second engine. The popup and Shelf should create/edit the same canonical destination/shortcut records, and Simple/Narrow/Depth should project those records through one controlled Chrome-native registrar.

For S3-compatible connections, the future V3+1 engine should support independent sibling provider roots such as **Cloudflare R2**, **MEGA S4**, and further S3-compatible connections through standard adapters. Google Drive, Dropbox and OneDrive remain independently implemented provider systems. They may adopt the same understandable Simple/Narrow/Depth menu conventions, but they must **not depend on V3/S3 internals**. They share only the narrow native-menu registration protocol/infrastructure.

**IF** a destination already has a configured native save action, **THEN** right-clicking it saves immediately.
**IF** a new destination is chosen and **No** is selected, **THEN** save once without adding a menu record.
**IF** **Yes** and Simple/Narrow/Both are chosen, **THEN** create the corresponding independent menu action configuration without changing the real remote location.
**IF** the user later wants to edit labels, modes, aliases, Depth or ordering, **THEN** use **Shelf → Destinations**.

### Scope and priority

**P1 UX proposal for future V3+1**, to evaluate after the **source-first V3 Mechanics Atlas** and current-vs-vision audit are reviewed. The current audit is documentation/evidence only, not authorization to rip out or rewrite the functioning V3 UI.

We aim for a fast, legible experience with minimal deliberate setup, stable exact routing, clear verified success, and no hidden Browse Folders prerequisite. Preserve BOOT, Shelf startup, History, Explorer, other clouds, saved configuration and current verified remote-save behavior.

**Why it matters:** Ordinary users should not have to design a nested right-click menu to benefit from REDOWN. Their menu should grow naturally from the cloud destinations they choose, and the Shelf should offer the right level of control afterward.
