## P0 — Make Google Drive as seamless as the other clouds

- [ ] **P0.1 — Audit and eliminate the special Google Drive transfer tab.** Current Google Drive flow still opens a browser-mediated transfer page and asks users to keep it open. Inspect and document the real Chrome MV3 service-worker/content-script/offscreen-document constraints and the existing Google Drive API upload pipeline. Target experience: the owner signs in once, then **right-clicks a supported file → REDOWN → Google Drive → saved**, with no transfer page, no separate foreground tab, no repeated permission confirmation during a healthy authorized session, and no mandatory user interaction after the save command. Show progress in the Shelf/History without requiring the Shelf to stay open. Never claim browser-side work is running after a terminated service worker unless its resumable state and recovery are truly implemented.
- [ ] **P0.2 — Remove REDOWN's artificial 32 MiB file cap; stream and resume large supported files.** Determine Google Drive's real current upload API limits, resumable-session constraints, maximum per-request chunk sizes, available memory, signed/authenticated source limitations, and Chrome extension lifecycle. Support files as large as the permitted service and browser transfer path can safely handle, ideally approaching Drive's service maximum when actually testable. No in-memory whole-file buffering, invented unlimited support or false completion. Verify small, large, interrupted, resumed and uncertain transfers with accurate byte counts and durable receipts.
- [ ] **P0.3 — Save to the selected Drive root, never create an unwanted REDOWN folder.** No automatic `REDOWN`, `Apps`, or similar folder just to perform a normal save. Respect only explicitly authorized Google Drive scopes and actual accessible files/folders (prefer `drive.file` as the owner's public-app verification goal). Do not scan or modify a user's entire Drive or silently request broader access to implement root saving. If the chosen scope cannot support an operation, disclose the limitation and use the least-privilege supported flow; do not pretend consent or provider capabilities exist.
- [ ] **P0.4 — Keep source provenance private to REDOWN.** Gather the original source/page/frame/link URLs inside REDOWN as necessary to capture bytes and maintain trustworthy History; **never add those source URLs to Google Drive API upload metadata**. Google receives only the requested content, filename and minimal required destination metadata. A browser-fetched source still reveals ordinary network information to its origin server; do not promise network anonymity. Avoid extra provider permissions, prompts and unrelated tracking.
- [ ] **P0.5 — First-run and reconnection UX.** One deliberate Google OAuth authorization, persistent session with safe token refresh when permitted, and repeat right-click saves until genuine revocation/expiry requires reconnection. Handle inaccessible URLs, cookies/authenticated sources, redirects, blob/media objects and failed origins truthfully; never present `data:`, `blob:`, protected streams or cross-origin captures as universally available without proven byte access. Keep source-capture constraints independent of the Google Drive upload API.
- [ ] **P0.6 — Native menu isolation and reliability.** Preserve the protected V3 right-click engine, native shared menu authority, Cloudflare R2 TRUE REMOTE implementation, Dropbox/OneDrive integrations and provider-local Home behavior. Changes to Drive must be isolated, additive and evidence-backed. Handle cancel/retry/resume, Keep Both conflicts, file extensions, extensionless filenames, and exact History **GO TO** to the verified saved Drive object. No accidental Google Drive folder creation or cross-cloud routing.
- [ ] **P0.7 — Acceptance before checking this item complete.** Test fresh Chrome profile/install, connected session, repeated right-click saves, browser closed/reopened, service-worker suspensions, network interruption, small and multi-GB transfer when testable, filename/extension integrity, root placement, private metadata, History receipts/GO TO, no unwanted transfer tab, no recurring permission prompts, and concurrent sessions. Record actual API requests (with secrets redacted), SHA-256 or appropriate integrity evidence, saved Drive file ID and read-back confirmation. Mark unsupported source types explicitly; test on real installed Chrome, not just unit mocks.

**Owner's experience standard:** Google Drive should feel like Cloudflare, Dropbox and OneDrive from the Shelf: **connect once, right-click, save, and go about your day.** This is a quality target, not a claim that other providers are already defect-free.

## IDEAS IMPORTANT — AMEOBO living mascot and soothing kinetic UI

- [ ] **Generative mascot interactions and standardized creator submissions (100 × 100 vision).** Develop a composable foundation of approximately 100 initiating action primitives and 100 response primitives, yielding up to 10,000 *theoretical* ordered pairings, further varied by mascot adapters, body/contact planes, personality, timing, theme/skin, and sound. Build **submission infrastructure** with a documented versioned interaction manifest/schema, semantic action and reaction taxonomy, contact anchors/surfaces, pose/angle requirements, animation timings/transitions, sound-cue mappings, capability negotiation, compatibility checks, resource budgets, validation/conformance tests, safe sandboxed asset packaging, and review/moderation rules. Creator-authored compliant submissions should be reusable across participating mascots and apps rather than hardcoded for AMEOBO. A deterministic/seeded, weighted interaction director must compose **coherent** encounters with spatial alignment, continuity, cooldowns, graceful fallbacks, and repetition controls, not arbitrary randomized clips. Example: Framzy pats AMEOBO at a declared surface, producing localized chrome undulation, jiggle, laughter and an optional reciprocal response. Provide a catalog/registry, versioning, discoverability, preview/testing tools, saveable favorite sequences and revocation/compatibility handling. Start with a small verified library before scaling; 10,000 combinations are mathematical potential, not a promise of distinct polished scenes. Keep interactions opt-in, nonblocking and isolated from file access, extension permissions and provider credentials. **Future concept only.**
- [ ] **Interoperable reaction architecture: plane-to-plane, surface-to-surface, reaction-to-reaction timing.** Define a stable, versioned spatial and temporal contract that outside creators can reliably build against. Each compliant character/skin declares coordinate systems, local planes, contact surfaces and normals, named interaction anchors, pose/angle ranges, reach, movement constraints, clip entry/exit states, timings, contact windows, reaction triggers, and synchronized audio/VFX cues. A shared choreography coordinator aligns the participants' transforms and contact moments, negotiates compatible capabilities, sequences reactions and counter-reactions, and blends into valid fallback motions when geometry or animation assets differ. Supply reference adapters, sample characters, a conformance test harness, visual contact/timeline debugger, schema validation and compatibility/version rules, so community animations **interoperate predictably** instead of requiring pair-specific hardcoding. “Always work” is an engineering acceptance goal within declared compatible capabilities, not a promise that arbitrary animations can connect without appropriate assets. Keep the generic API independent of AMEOBO and the file systems. **Future architecture proposal, not implemented.**


- [ ] **AMEOBO as useful, eyeless chrome companion from day one.** Start with a lightweight floating, iridescent, rainbow-chrome blob with no eyes or facial rig. Communicate through fluid motion, ripples, squish/stretch, subtle sound and short comic speech bubbles. He is both a calming, playful stress toy and a practical interface guide, not decoration alone.
- [ ] **Morphing living arrow and contextual guide.** AMEOBO can smoothly stretch into a large recognizable pointer to indicate real, relevant next steps, such as Activate Buckets, Save Changes/Apply, setup, errors, Lightbox and newly introduced features. Return softly to blob form afterward. Never obscure controls, fabricate required steps or interrupt normal file workflows. Use contextual event triggers, not intrusive guessing about user intent.
- [ ] **Deliberate, shortcut-safe interactions.** Allow holding a configurable modifier/button while hovering over AMEOBO and clicking/dragging to pick him up, stretch him, toss him and set him down; allow tickling or poking to elicit giggles, dents, bobbles, surprised squashes and playful speech bubbles (e.g. “Hey, that tickles! Stop! Haha!”). Use explicit hit-testing and avoid conflicts with Chrome/OS keyboard shortcuts, Explorer selection, drag-and-drop and file actions. No unsolicited mouse capture.
- [ ] **Mesmerizing geometric loading and seamless transitions.** Replace repetitive generic loading spinners where appropriate with beautiful evolving geometric compositions: folding rings, blooming shapes, smooth tessellations and morphing chrome forms. Use coherent soothing motion between Shelf, Explorer, menus and progress/completion states so users may enjoy returning just for the experience. Progress must be truthful; animation must never delay a completed action or falsely imply successful transfer.
- [ ] **AMEOBO grows with REDOWN over time.** AMEOBO naturally floats from place to place across the interface, smoothly morphing shape as he travels, rests, points, plays or responds to events. His animation library is deliberately **expandable**: every new REDOWN feature or milestone may add new idle loops, transformations, transitions, reactions and movement patterns. Do not treat his launch animation set as final. Add behaviors incrementally through AMEOBO's own adapter and animation registry while keeping the generic Mascot API stable and mascot-independent. New animations should not require reworking file operations or the core interaction contract.
- [ ] **Physically expressive personality without costly AI.** Use lightweight spring/inertia/deformation effects for hovering, lifting, tossing, landing and recovery; playful idle behavior and occasional rare surprises; small contextual reactions to saves, errors and user interaction. Begin with a deterministic/event-driven state machine rather than servers or AI inference. Optional session-local response to repeated tickling/tossing may make him feel alive without unnecessary tracking.
- [ ] **Generic, mascot-independent Mascot API with AMEOBO adapter.** The Mascot API is a logical, abstract interaction contract, **not AMEOBO's own engine**. Define reusable actions/capabilities such as `pickUp`, `push`, `jiggle`, `poke`, `tickle`, `drag`, `toss`, `idle`, `pointTo`, `highlight`, `reactSuccess`, `reactError`, `enterTransition` and `exitTransition`; implementations choose how each action looks, sounds and behaves. **AMEOBO has his own adapter** translating those generic calls into chrome-blob morphing, physics, reactions and speech bubbles. Other future mascots can supply different adapters without changing the API or REDOWN's application logic. Keep interaction routing/shortcuts, event hooks and accessibility in the shared contract; keep mascot-specific rendering, geometry, sounds, animation and physics in adapters. Implement after Boot API and right-click API stability work, isolated from V3 menu registration, provider uploads and core file operations, and compatible with a future bounded Skin API.
- [ ] **Multi-mascot interaction architecture (future).** The generic Mascot API must eventually support **multiple mascot instances simultaneously**, including mascots interacting **with each other**, not only with the user or UI. Provide mascot-independent identities, position/state and capability discovery, event routing, and safe interaction requests (e.g. approach, greet, nudge/push, play, react, collaborate) with consent/priority and collision/conflict handling. Each mascot's adapter translates generic events into its own animations and personality. AMEOBO remains just one adapter. Design the contract to accommodate this extension without requiring multi-mascot behavior in v1; avoid hard-coding a single global mascot, AMEOBO-specific assumptions or direct adapter-to-adapter coupling. Preserve file-operation isolation and performance controls.
- [ ] **Cross-app mascot neighborhood: REDOWN + Chute + FrameChute (future).** When a user has the respective apps installed/entitled, offer their mascots as optional residents of a small shared desktop/browser UI corner: AMEOBO (REDOWN), the Chute mascot, and Framzy (FrameChute). Users can choose which mascots inhabit the corner. Multiple mascots should autonomously but gently greet, explore, interact, tease, chase, play-fight, collaborate, surprise each other and occasionally surprise the user with charming spontaneous animations. Behaviors should feel context-aware and varied, using a lightweight event/behavior scheduler and mascot-specific adapters rather than requiring constant AI inference. Coordinate shared state and inter-mascot interactions via the generic Mascot API, with no hardcoded dependency on AMEOBO. Detect connected products with explicit permission and minimum necessary data; do not imply cross-extension UI or ownership detection works automatically without supported permissions/integration. Keep surprises opt-in, quiet by default, nonblocking, non-destructive, accessible, easily paused/muted, and never intrusive during file operations. Let the library of playful interactions expand with each product release. **Idea only, not a launch requirement.**
- [ ] **Theme-reactive lighting on AMEOBO and other reflective mascots.** Each REDOWN theme should define an ambient light palette, highlight colors, brightness/contrast and optional glow characteristics that visibly **bounce off and reflect across AMEOBO's floating chrome surface** as he moves, spins, stretches and morphs. Reflections must respond smoothly to theme switches and nearby interface accents without turning into expensive real-time ray tracing. Use lightweight shader/environment-map, gradient or CSS/WebGL fallback techniques where appropriate, consistent with browser performance and reduced-effects settings. Define theme lighting as generic data consumed by each mascot's own visual adapter, never hardcode AMEOBO behavior into the shared Mascot API. Plan for multiple mascots with different reflective/material responses. **Idea only, not implemented.**
